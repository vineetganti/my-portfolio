## TL;DR

- **Agents are essay exams, not maths papers.** Outputs vary, quality depends on who asks, and many things must be right at once, so exact-match tests don't work. Evaluate many realistic questions, **part by part**.
- **Three gulfs** explain most mistakes: comprehension (you never looked at the inputs), specification (the prompt says too little), generalization (new inputs break it).
- **Four component evals** on one inventory advisor: routing (3 of 3 on both providers ✅), the prompt (Version 1 against Version 2, LLM-judged), search (Recall@k needs no model: 50%, 60%, 80% for k = 1, 2, 3 ✅) and tool calls (Groq 12 of 12; Claude 11 of 12, because Claude Code had already told it today's date ✅).
- **The judge is a component too.** With Groq's judge the improved prompt scored *worse* (100% → 85%); with Claude's judge, better (67% → 89%). On the same 18 answers the two judges agreed 61% of the time, against 54% expected by chance: **Cohen's kappa 0.16**, "slight". ✅
- **Check every scorer, including the scoring code:** the course's own fixes included token counts that were always 0 and an attribution check that passed nearly everything. 📘

## Part 1: why evaluating an agent is hard

### Three gulfs

![The three gulfs between a developer, the data and the model. Comprehension, between developer and data: you haven't looked at what users actually ask. Specification, from developer to model: what you want is loosely written in the prompt, as in prompt Version 1, 'Answer the question.' Generalization, from data to model: the model behaves differently on inputs it hasn't seen, such as a question about a supplier that is really a reorder question. Evals exist to find which gulf a failure fell into.](/images/ai-llms/agentic-ai/agent-evaluation/three-gulfs.svg)

📘 From the lecture: **comprehension** sits between you and your data (you haven't read what users actually ask), **specification** between you and the model (what you want is loosely written in the prompt), **generalization** between the data and the model (it behaves unpredictably on inputs it hasn't seen).

<Callout type="analogy" title="A new cook">

You never looked at what customers order (comprehension), you told the cook "make it tasty" (specification), and the cook who nails dal makhani in training falls apart when someone orders it without onion and garlic (generalization).

</Callout>

### Why traditional tests fall short

You can't write `assert agent("Should we reorder?") == "..."`: there are many good answers, worded differently each run, and "good" depends on who's asking. Classic ML testing doesn't fit either, because it scores one label against a fixed answer. What works instead, per the lecture: context-specific metrics, many test cases, checks that accept any correct answer, and a separate test for each **component**, because an agent can have a perfect router and a broken prompt. 📘

### Two kinds of metric

| | Reference-based | Reference-free |
| --- | --- | --- |
| **Needs** | A known good answer ("golden" output) | Only rules or properties |
| **Examples here** | Expected key points for the judge; the passages a question needs (Recall@k); the expected tools | Groundedness (does the answer stick to what was retrieved?) |
| **Like** | A maths paper with an answer key | An essay with a marking scheme |

### Test data and error analysis

📘 Two ideas from the lecture that the code doesn't run but every eval needs:

- **Synthetic test questions in two steps.** First list the *dimensions* along which real users differ (role, product, urgency, how they phrase things), pick a spread of combinations (*tuples*) with a fixed seed, and only then ask a model to phrase each tuple as a real message. Asking a model directly for "20 test questions" gets you 20 variations of the same polite question.
- **Error analysis before metrics.** Read failed answers and write a short note on each (*open coding*), group the notes into a few categories (*axial coding*), count them, and fix the most frequent problem first. A simple review screen makes this fast; the course ships one, `annotator.html`, where a reviewer clicks pass or fail and writes why.

## Part 2: four component evals

![Four component evals, each built the same way: a small test set with known good answers, run one part of the agent, score each answer, report. The router gets questions with the correct route and is scored on routes. The system prompt, Version 1 against Version 2, is scored by an LLM judge on accuracy, clarity and completeness. Search plus answer is scored on Recall@k without a model, then by a judge on relevance, groundedness and correctness. Tool calling is scored on precision, recall, calls per task, success, latency and cost. A last step checks the judge itself against a second rater with Cohen's kappa.](/images/ai-llms/agentic-ai/agent-evaluation/component-evals.svg)

The running example is a warehouse **reorder advisor**. Every eval file follows the same four steps: a small test set with known good answers, run one part of the agent, score each answer, print a report and save a CSV.

### The router

`langgraph_router.py` is a LangGraph graph whose first node must pick exactly one of three specialists (reorder, forecast, supplier), each the same model with a different system prompt. ✅ All three demo questions were routed correctly on both providers, including "Supplier A is cheaper but takes 30 days… which is better?" to `supplier`. 📘 The lecture's nine-question version misses one: "Our supplier keeps delivering late. Should I raise my reorder point?" mentions a supplier but is really a reorder question, and the router has no "other" route for questions that fit none.

### The prompt: Version 1 against Version 2

```python title="prompt_evals_inventory.py (the judge, shortened)"
eval_prompt = f"""Evaluate this inventory reorder advisor response with STRICT binary scoring (0=Fail, 1=Pass).
    Question: {question}
    Expected Key Points: {expected_answer}
    Actual Response: {actual_response}
    - Accuracy: Is the reorder recommendation correct with NO errors or misleading statements? (0 or 1)
    - Clarity: Would a warehouse manager act on this WITHOUT further questions? (0 or 1)
    - Completeness: Does it address the SPECIFIC edge case or nuance in the question? (0 or 1)
    Respond ONLY with JSON in this exact shape:
    {{"Accuracy": 0 or 1, "Clarity": 0 or 1, "Completeness": 0 or 1, "Reason": "one short sentence"}}"""
```

Version 1 of the advisor's system prompt says only "Answer the question"; Version 2 spells out what a good answer contains. Nine tricky questions each, judged pass or fail on three criteria. The same model writes the answers and judges them. My two runs:

| Overall pass rate | Version 1 | Version 2 | Verdict |
| --- | --- | --- | --- |
| ✅ Groq gpt-oss-20b (answers and judge) | 27/27 (100%) | 23/27 (85%) | "Version 2 is worse" |
| ✅ Claude Haiku 5.5 (answers and judge) | 18/27 (67%) | 24/27 (89%) | "Version 2 is better" |

Opposite conclusions from the same code. The judges' one-line reasons show why: Claude's judge failed answers for things like naming FIFO instead of FEFO for perishables, or opening with "Yes, that's correct" to a reorder point that ignores variability; Groq's judge passed nearly everything and failed one Version 2 answer as "Contains extra real-world caveats that could confuse a manager". Two caveats before reading anything into the numbers: each judge graded *its own provider's* answers, so model and judge are tangled together here, and nine questions per version means one answer moves a score by 11 points. The fair comparison is two judges on the same answers, which is the last section of this part.

### Search: Recall@k, then a judge

`rag_evals_inventory.py` has twelve short passages about inventory planning and five questions, each listing which passages it needs. **Recall@k** counts how many of the needed passages were retrieved, with no model involved; then a judge scores the answer for relevance, groundedness and correctness. Three configurations: k = 1 with a minimal prompt, k = 2 structured, k = 3 with a "use only the context" instruction.

| | Recall@k | Groq judge: grounded / overall | Claude judge: grounded / overall |
| --- | --- | --- | --- |
| A: k = 1 | 50% | 40% / 80% | 0% / 53% |
| B: k = 2 | 60% | 80% / **93%** (best) | 0% / 47% |
| C: k = 3 | 80% | 80% / 93% | 40% / **80%** (best) |

![The same eval code scored by two different judges. Prompt evals: with Groq gpt-oss-20b as the judge, Version 1 passed 100 percent and Version 2 85 percent, so the improved prompt looked worse; with Claude Haiku 5.5 as the judge, Version 1 passed 67 percent and Version 2 89 percent. Each judge graded the answers written by its own provider. RAG evals: Recall@k was identical for both runs, 50, 60 and 80 percent for k of 1, 2 and 3, because retrieval is local; but the Groq judge picked configuration B as best at 93 percent and the Claude judge picked C at 80 percent, marking no answer in A or B as grounded.](/images/ai-llms/agentic-ai/agent-evaluation/judges-disagree.svg)

✅ Recall@k came out identical on both runs, because retrieval uses the local embedding model and no LLM; it rises with k, as it should, and explains why k = 1 does badly (most questions need two passages). Everything a judge touched disagreed: Groq's picked B, Claude's picked C, and Claude's marked **no** answer from A or B as grounded ("the answer adds unsupported claims"). A metric that needs no model is worth having for exactly this reason. 📘 Shivank's version embeds the twelve passages once instead of once per search (the original repeated 180 embedding calls over 15 runs) and added the Recall@k column.

### Tool calls: right tool, right number of times, at what cost

`tool_evals_inventory.py` gives a LangChain agent six calculators (reorder point, EOQ, safety stock, days of supply, ABC class, today's date) and twelve scenarios with the tools each should use: single-tool, multi-tool, ambiguous wording, and two that need no tool.

| | Groq gpt-oss-20b | Claude Haiku 5.5 |
| --- | --- | --- |
| Tool precision / recall | 1.000 / 1.000 | 0.917 / 0.917 |
| Optimal number of calls | 100% | 91.7% (one task under-called) |
| Answers that used the tool's result | 1.000 | 0.900 |
| Average latency per task | 6.5 s | 6.1 s |
| Tokens per task | about 1,000–1,850 | about 2,300–5,350 |
| Total cost (12 tasks) | $0.0015 | $0.0068 (API-equivalent) |

✅ The one miss is a finding about my setup, not the model: asked "What is today's date? I need to schedule a delivery", Claude answered without calling `date_info`, because Claude Code had already put today's date in its prompt ([why](/blog/giving-agents-tools#the-same-loop-on-two-providers)). By the test's definition that's under-calling; by any user's, the answer was right. An eval's expected labels encode assumptions about what the model can know, and the environment can break them. Claude's token counts include Claude Code's wrapper and the emulated tool calls, which is why its cost per task is four to five times Groq's.

📘 This file had the course's most instructive bugs, all fixed before I ran it:

| Original | What went wrong | Now |
| --- | --- | --- |
| Token counts read from `result.llm_output` | The result is a dictionary, so the check was always false: **tokens and cost were always 0** | Real counts from each reply's `usage_metadata` |
| Attribution: do the tool output's first 5 words appear in the answer? | Words like "=" and "units" appear in almost any answer, so it passed nearly everything | Does the tool's main number appear in the answer? |
| `execution_time_ms` per tool call | Stored the whole task's time on every call | One latency per task |
| Made-up prices | Cost numbers you couldn't trust | List prices from one setting |

A scorer that always passes, or always reports zero, looks exactly like a good result. Test the eval code the way you'd test the agent: include a case built to fail.

### Checking the judge

![Two LLM judges grading the same 18 answers, the Claude run's prompt-eval answers. Claude's judge passed 10 and failed 8; Groq gpt-oss-20b's judge passed 15 and failed 3. They agreed on 11 of 18: both passed 9, both failed 2. Raw agreement was 61 percent, but agreement expected by chance, given how often each passes, was 54 percent, so Cohen's kappa was 0.16, slight agreement. Most disagreements were answers Claude's judge failed for a missing nuance and Groq's judge passed.](/images/ai-llms/agentic-ai/agent-evaluation/kappa-matrix.svg)

The course's last step checks the judge against a person: `annotator.html` lets a reviewer mark each saved answer pass or fail, and `judge_agreement.py` computes **Cohen's kappa**, agreement corrected for chance:

```python title="judge_agreement.py"
def cohens_kappa(a, b):
    n = len(a)
    observed = sum(x == y for x, y in zip(a, b)) / n
    labels = set(a) | set(b)
    chance = sum((a.count(l) / n) * (b.count(l) / n) for l in labels)
    return observed, chance, (observed - chance) / (1 - chance) if chance < 1 else 1.0
```

Raw agreement misleads when one rater passes almost everything: if both say "pass" 90% of the time, they agree on 82% of answers by luck alone. Kappa subtracts that. The usual reading (Landis and Koch): up to 0.2 slight, 0.4 fair, 0.6 moderate, 0.8 substantial, above that almost perfect. 📘

I didn't review the answers myself for this post. Instead I put a **second LLM judge** in the reviewer's place: the 18 answers from the Claude run, already judged by Claude, re-judged by Groq's `gpt-oss-20b` with the same judge prompt, then the course script run unchanged. Its "human" column held the second judge.

```text output
                 Human: pass   Human: fail
  Judge: pass             9             1
  Judge: fail             6             2

Raw agreement        : 61%
Agreement by chance  : 54%   (judge passes 10/18, human passes 15/18)
Cohen's kappa        : 0.16  → slight agreement
```

✅ The two judges agreed on 11 of 18 answers, barely above what their pass rates give by chance. Six of the seven disagreements were answers Claude's judge failed for a missing nuance ("never recommends a rolling 4–8 week average", "opens with 'Yes'") and Groq's passed. Neither is shown to be right; that is what a human review is for. What the run does show is that "the LLM judge says 89%" is a statement about the judge as much as the answers. The explainer's own list of known limits makes the same point: 📘 the judge grades its own model's answers, which can make it lenient, and a larger judge is a common upgrade that kappa will tell you whether it helped.

## Part 3: Evaluating with AgentCore Evaluations

A trace tells you what happened. It doesn't tell you whether the answer was any good. **AgentCore Evaluations** reads an agent's traces from CloudWatch and scores them with an LLM judge: "traces from these agents are converted to a unified format and scored using LLM-as-a-Judge techniques for both built-in and custom evaluators" ([how it works](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/how-it-works-evaluations.html)).

![One session of the travel agent holds four traces, one per prompt: flights, a hotel, the weather and an out-of-scope Python question. Each of the first three has a model call, a tool call and a second model call; the fourth is a single model call, a refusal. Session-level evaluators read the whole conversation, trace-level evaluators score each question and answer, and tool-call evaluators score each tool call. The judge reads these spans from CloudWatch about three minutes after the last call](/images/ai-llms/agentic-ai/agent-evaluation/eval-levels.svg)

The lab's agent is a travel assistant on AgentCore Runtime, deployed as in [the last post](/blog/agents-to-production), with three mock tools and one rule in its prompt: "Only answer questions related to travel — flights, hotels, and weather. For anything outside travel, politely decline". The toolkit listed 19 built-in evaluators and 13 third-party ones:

| Level | Built-in evaluators | Measures |
| --- | --- | --- |
| **Session** | GoalSuccessRate, FailureAnalysis, three Trajectory matches (exact, in order, any order) | Did the conversation achieve the user's goals; did the agent take the expected path |
| **Trace** | Correctness, Faithfulness, Helpfulness, ResponseRelevance, Conciseness, Coherence, InstructionFollowing, Refusal, Harmfulness, Stereotyping | Quality and safety of each answer |
| **Tool call** | ToolSelectionAccuracy, ToolParameterAccuracy, SkillSelectionAccuracy, SkillInstructionFollowing | Right tool, right arguments |
| **Third party** | DeepEval (bias, toxicity, PII leakage, task completion, …), AutoEval | Extra metrics behind the same API |

### A custom judge for the agent's scope

Generic evaluators don't know your product's rules. The lab's custom evaluator does:

```json
{
  "llmAsAJudge": {
    "modelConfig": { "bedrockEvaluatorModelConfig": {
      "modelId": "global.anthropic.claude-haiku-4-5-20251001-v1:0",
      "inferenceConfig": { "maxTokens": 500, "temperature": 1.0 } } },
    "instructions": "You are evaluating the quality of a travel assistant's response. … **IMPORTANT**: The assistant should ONLY answer travel-related questions. If the user asks about non-travel topics and the assistant answers them, classify as Very Poor.\n\nContext: {context}\nCandidate Response: {assistant_turn}",
    "ratingScale": { "numerical": [
      { "value": 1.0,  "label": "Very Good", "definition": "Response is accurate, helpful, and directly addresses the travel question …" },
      { "value": 0.75, "label": "Good", … }, { "value": 0.5, "label": "OK", … }, { "value": 0.25, "label": "Poor", … },
      { "value": 0.0,  "label": "Very Poor", "definition": "Response is completely wrong, irrelevant, or answers out-of-scope questions." } ] }
  }
}
```

`{context}` and `{assistant_turn}` are placeholders that the service fills from the trace. A trace-level evaluator gets those two, and "the instruction must include at least one placeholder". The service also appends its own instructions for the output format, so the judge always returns a reason and a score ([create an evaluator](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/create-evaluator.html)). Evaluator names must be unique in the Region, so the lab adds a random suffix.

```python
eval_client = Evaluation(region=region)
custom_evaluator = eval_client.create_evaluator(name=f"travel_response_quality_{uuid.uuid4().hex[:6]}",
                                                level="TRACE", config=eval_config, …)
```

### Running the evaluation

All four prompts share one session id, so they form one conversation:

```python
session_id = str(uuid.uuid4())
test_prompts = [
    "What flights are available from New York to London?",     # in scope
    "Can you recommend a mid-range hotel in Paris?",           # in scope
    "What is the weather like in London right now?",           # in scope
    "Can you help me write a Python script to sort a list?",   # out of scope
]
for prompt in test_prompts:
    runtime.invoke(payload={"prompt": prompt}, session_id=session_id)

time.sleep(180)   # the judges read spans from CloudWatch, which take a few minutes to arrive

goal = eval_client.run(agent_id=agent_id, session_id=session_id, evaluators=["Builtin.GoalSuccessRate"])

                          evaluators=["Builtin.Correctness", "Builtin.Helpfulness"])
custom = eval_client.run(agent_id=agent_id, session_id=session_id, evaluators=[evaluator_id])
```

Each score comes with the judge's reasoning, and the reasoning is where the learning is. **Correctness** checked every fact against the tool results: the judge saw the tool output in the trace and compared it to the answer. **Helpfulness** marked the refusal down to 0.50, Neutral/Mixed, because a generic judge only sees that the user didn't get a Python script. <Callout type="warn" title="The test that couldn't fail">

The notebook promises that the custom evaluator will "catch the out-of-scope answer that generic metrics miss", scoring it Very Poor. It didn't, and it couldn't: Claude Haiku followed its system prompt and **refused**, so there was no out-of-scope answer to catch. The custom judge was working correctly. The test set just had no failing case. To see an evaluator catch something, you need a case that actually fails, for example the same agent with the scope line removed from its prompt. An evaluation that only ever passes tells you less than it seems to.

</Callout>

### On-demand, online and batch

This lab ran **on-demand** evaluations: you name the session, and the results come back to your code (the lab also saved them as JSON). AWS describes two other modes ([evaluation types](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations-types.html)):

| Mode | When it runs | Where the results go |
| --- | --- | --- |
| **On-demand** | When you call it, on the sessions or traces you choose | Back to your code |
| **Online** | Continuously, on a sample of live traffic (for example 10% of sessions) | A CloudWatch log group (`/aws/bedrock-agentcore/evaluations/results/…`) and metrics in `Bedrock-AgentCore/Evaluations` |
| **Batch** | One asynchronous job over many sessions | Per job |

For online results in the console: **GenAI Observability → Bedrock AgentCore**, choose the agent, then the **Evaluations** tab ([results and output](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/results-and-output.html)). The judge must be a Bedrock model, which is why the course's Groq edition uses the open-source [Strands Evals](https://github.com/strands-agents/evals) SDK with a Groq judge instead.

## Things that can trip you up

- **One good answer as evidence.** Run many realistic questions; one run of a non-deterministic system proves nothing.
- **A judge grading its own model.** It can be lenient on answers in its own style. Use a different, ideally stronger, judge and measure agreement.
- **Raw agreement.** Two raters who both pass almost everything agree by chance. Report kappa.
- **Scorers that can't fail.** Tokens always 0, attribution always true: include a case built to fail and check it does.
- **Expected labels that assume what the model can't know.** Claude Code gave the model today's date, so "should call `date_info`" was wrong for that environment.
- **Small test sets.** With nine questions, one answer moves a score by 11 points. Grow the set before trusting a difference.
- **Pass/fail hides partial credit.** Keep the judge's one-line reason; it's what you read during error analysis.
- **Overwritten results.** The eval scripts write the same CSV every run; copy it before running another provider.
- **An evaluator that never fails** (AgentCore). The test set has no failing case; add cases built to fail.
- **A generic judge marks a correct refusal down** (AgentCore). It doesn't know your agent's scope; write a custom evaluator.

## What I learned

The most important component of an eval is the judge, and it is the one people test least. The same code reached opposite verdicts on the same prompt depending on which model graded it, and the measurements that held steady across providers were exactly the ones with no model in them: routing, Recall@k, tool choice. Where a check can be a rule, make it a rule.

## What I'd do differently

Spend the first hour on the judge: twenty answers labelled by hand, the judge run on the same twenty, kappa computed. Only then run the comparisons. And keep each run's CSV under a name that says which model wrote the answers and which judged them.

## Summary

An agent is evaluated like an essay exam: many realistic questions, a written idea of what good looks like, and a score for each part of the agent separately. Reference-based checks (routes, needed passages, expected tools) are stable and cheap; judged checks (accuracy, groundedness) cover what rules can't, but the judge is itself a component that must be checked against a person, and two judges here agreed only slightly beyond chance. On AWS, AgentCore Evaluations does the judging over an agent's traces, with built-in or custom evaluators.

### Concepts at a glance

| Term | In one line |
| --- | --- |
| **Eval** | A repeatable test of how well an agent, or one part of it, does its job |
| **Golden set** | Test questions with the answers, passages or tools you expect |
| **Reference-based / reference-free** | Compared with a known answer / checked against rules or properties |
| **Component eval** | A test of one part (router, prompt, retrieval, tools) on its own |
| **Recall@k** | Of the passages a question needs, how many the top k retrieved |
| **LLM-as-judge** | A model that scores answers against a rubric |
| **Error analysis** | Read failures, label them, group, count, fix the biggest group first |
| **Cohen's kappa** | Agreement between two raters after removing agreement expected by chance |
| **AgentCore Evaluations** | AWS's service that scores an agent's traces with built-in or custom judges |

### Test yourself

<details>
<summary>Prompt Version 1 says only "Answer the question." Answers are correct but miss the edge case. Which gulf is that?</summary>

Specification: the prompt never said what a good answer must contain. Version 2 closes that gulf.

</details>

<details>
<summary>Groq's judge preferred Version 1 and Claude's preferred Version 2. What would you do before choosing a prompt?</summary>

Grade a sample of the same answers yourself, compute each judge's kappa against your labels, and trust the judge that agrees with you; and grow the test set beyond nine questions.

</details>

<details>
<summary>Why did Recall@k agree across both runs when everything judged disagreed?</summary>

It needs no model: it compares the retrieved passage numbers with the ones each question needs, and retrieval used the same local embeddings in both runs.

</details>

<details>
<summary>Two judges agree on 61% of answers. Why can that still be "slight" agreement?</summary>

When one judge passes 15 of 18 and the other 10 of 18, they would agree on about 54% by chance alone. Kappa measures only the agreement above that: 0.16 here.

</details>

<details>
<summary>The original tool eval reported a cost of $0 for every run. Why is that worse than a crash?</summary>

It looks like a result. A scorer that silently returns zero or always passes hides problems; a crash at least tells you something is broken.

</details>

<details>
<summary>How does AgentCore Evaluations know what the agent did?</summary>

It reads the agent's traces from CloudWatch: the prompts, tool calls, tool results and answers. That's why the lab waits about three minutes after the last call, and why Transaction Search must be on.

</details>

<details>
<summary>What are the three evaluator levels, with an example of each?</summary>

Session (the whole conversation, for example GoalSuccessRate), trace (each question and answer, for example Correctness or Helpfulness) and tool call (each tool use, for example ToolSelectionAccuracy).

</details>

<details>
<summary>Why did Helpfulness score the Python refusal 0.50 while the custom judge scored it 1.00?</summary>

The generic judge only saw that the user didn't get what they asked for. The custom judge's rubric says the assistant must stay within travel, so a polite refusal is the correct behaviour.

</details>

<details>
<summary>The custom evaluator was meant to give the out-of-scope answer Very Poor. Why didn't it?</summary>

Because there was no out-of-scope answer: the agent refused. The judge worked correctly, but the test set had no failing case. To test an evaluator, include a case that should fail, such as the agent without its scope rule.

</details>
