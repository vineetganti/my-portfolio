LLMs are stateless by default. If you end a chat session and start a new one, the model has no memory of the earlier conversation. The only "memory" it ever has is whatever text is put back into its prompt. Memory, for an agent, is the machinery that puts the right information back into the prompt at the right time.

Without memory, every interaction feels transactional. With memory, an agent can keep track of what you asked a while ago, keep important facts across sessions, adapt to your preferences and stay on track in long-running work.

| Feature | Agents without memory | Agents with memory |
| --- | --- | --- |
| **Context** | Reset every time a session ends | Carried forward across sessions |
| **Personalisation** | Low; generic responses | High; tailored to the user's history |
| **Efficiency** | User must repeat information | Agent remembers and builds on past information |
| **User experience** | Feels like talking to a stranger every time | Feels like a continuous relationship with an assistant |

Memory is two posts in this series. This one is about **short-term memory**: one conversation, kept small enough to resend, and saved so it can continue later. [The next post](/blog/long-term-agent-memory) is about **long-term memory**: facts, experiences and procedures that outlive a conversation.

## TL;DR

- **A model call keeps nothing.** Memory is the app resending what matters. Asked for a dinner place with no history, both models had to ask where I was; with one earlier message resent, both suggested vegetarian places in Pune. ✅
- **Decide what, when, where, how and how much** before adding memory. "When" has two answers: write memory in the **hot path** (before replying, always fresh, slower) or **in the background** (later, in one batch). On Claude, the same three-message chat took 37.8 s one way and 18.7 s the other. ✅
- **Four ways to keep one conversation small:** a plain buffer, **trimming** to a token budget, **deleting** chosen messages, and **summarising** old ones. ✅
- **Test what you claim.** The course notebook says trimming loses the user's name but never asks for it. In its own conversation the name survives the trim; and with a slightly different conversation, its 300-token budget plus "start on a user message" kept zero messages on Groq. ✅
- **Saving the conversation** is a checkpointer's job: LangGraph saves a snapshot after every step, keyed by `thread_id`, and AgentCore Memory keeps those snapshots in AWS.

## Why a stateless model needs memory

### A model call keeps nothing

Each call to a model is a fresh start: it gets the text you send, writes a reply, and keeps nothing. If a chatbot seems to remember, the app is sending the earlier messages along again. The lecture shows it in a few lines:

```python title="m04_stateless.py (from the Memory lecture, ported)"
print("A:", ask([{"role": "user", "content": "Hi, I'm Priya. I'm vegetarian and I live in Pune."}]))
print("A:", ask([{"role": "user", "content": "Suggest a dinner place for me tonight."}]))   # a separate call

history = [{"role": "user", "content": "Hi, I'm Priya. I'm vegetarian and I live in Pune."}]
history.append({"role": "assistant", "content": ask(history)})
history.append({"role": "user", "content": "Suggest a dinner place for me tonight."})
print("A:", ask(history))                                                                   # history resent
```

✅ Asked separately, Groq replied with a list of questions ("Cuisine preference… Location… Budget…") and Claude said it didn't know where I was or what I liked. With the first message resent, both suggested vegetarian places in Pune; Claude named three and added that it couldn't check opening hours. Same model, same question: the only difference is the text that was sent along.

### Five questions before adding memory

| Question | What it asks | A food-delivery support bot (📘 the lecture's example) |
| --- | --- | --- |
| **What** | Facts, summaries of past events, or rules and style? | Refund rules, the user's preferences, last order arrived cold, apologise first |
| **When / who** | When are memories formed, and by whom? | The agent saves preferences during the chat; a nightly job summarises tickets |
| **Where** | In the prompt, a database, a vector store? | Rules in the system prompt, preferences keyed by user ID, old tickets in a vector store |
| **How** | How are they found again? | Preferences by user ID, similar tickets by meaning, only the last 90 days |
| **How much** | Size limits and pruning | At most 50 facts per user; tickets older than a year summarised, then deleted |

<Callout type="analogy" title="Organising a kitchen">

What to stock, when to restock, shelf or fridge, labels so you can find it, and throwing out what has expired.

</Callout>

### Writing memory: hot path or in the background

![Writing memory in the hot path versus in the background, measured on Claude Haiku 5.5 for a three-message chat. Hot path: before every reply, one extra model call extracts facts and saves them, so memory is fresh at once; the three replies took 37.8 seconds in all. Background: replies only, and one batch call extracts the facts afterwards; 18.7 seconds in all. Both saved the same two facts: a trip to Rishikesh with parents, and the mother cannot climb stairs.](/images/ai-llms/agentic-ai/how-ai-agents-remember/hot-vs-background.svg)

Memory can be written **in the hot path**, inside every turn before the reply, so it is fresh at once but every reply waits for an extra model call; or **in the background**, after the conversation or on a schedule, so replies are fast but new facts only reach future conversations later. The lecture's demo does the same three-message chat both ways:

```python title="m06_hot_vs_background.py (from the Memory lecture, ported)"
for msg in chat:                                   # hot path
    facts = json.loads(extractor.invoke(EXTRACT.format(messages=msg)).text)["facts"]   # extra call BEFORE replying
    memory += facts
    reply = llm.invoke(f"Known about the user: {memory}\nUser: {msg}").text

for msg in chat:                                   # background
    reply = llm.invoke(f"User: {msg}").text
facts = json.loads(extractor.invoke(EXTRACT.format(messages="\n".join(chat))).text)["facts"]   # later, once
```

| | Hot path | Background | Facts saved |
| --- | --- | --- | --- |
| ✅ Claude Haiku 5.5 | 37.8 s | 18.7 s | trip to Rishikesh with parents; mother can't climb stairs (both ways) |
| ✅ Groq gpt-oss-120b | 38.4 s | 34.4 s | the same two, plus, in the hot path only, "the user is looking for recommendations on which area to stay in" |

On Claude the trade-off showed up as the lecture describes: the hot path roughly doubled the total time. On Groq both totals were inflated, because my other Groq runs were competing for the same free-tier rate limit at the time, so its timings say little. Its facts say something, though: extracting from one message at a time, the hot path saved a *question* as if it were a lasting fact, which the batch extraction, seeing the whole chat, did not. Claude also dated the trip "around December 2026": it knows today's date, Groq's model doesn't ([why](/blog/giving-agents-tools#the-same-loop-on-two-providers)).

### Four kinds of memory

![The four kinds of agent memory as a tree. Memory splits into short-term and long-term. Short-term is the current conversation, one thread, answering 'what did we just say?'. Long-term splits into three: semantic memory holds facts and answers 'what is true?', episodic memory holds experiences and answers 'what happened last time?', and procedural memory holds skills and workflows and answers 'how do I do this?'. This post covers short-term memory; the next post covers the three long-term kinds.](/images/ai-llms/agentic-ai/how-ai-agents-remember/memory-types.svg)

| Type | Remembers | Agent example (📘 lecture) |
| --- | --- | --- |
| **Short-term** | The current conversation | The last 20 messages of this chat |
| **Semantic** | Facts: what is true | "Refunds are allowed within 30 days"; "this user is vegetarian" |
| **Episodic** | Experiences: what happened | "Last time, the shipping API rejected this order ID" |
| **Procedural** | Skills: how to act | "To track an order: validate the ID, then query the order database" |

<Callout type="analogy" title="Save points in a video game">

Short-term memory is the **save file** of a game in progress: quit, come back on another machine, continue where you stopped. Long-term memory is the **profile** that follows you across every game.

</Callout>

## Part 1: keeping one conversation under control

The model only sees what fits in its **context window**, and every message is paid for again on every turn. A long chat has to be cut down somehow. The course notebook `short_term_memory.ipynb` builds one five-turn conversation and then shrinks it four ways.

![Three ways to keep one conversation small, on the same ten-message chat. Trim keeps the most recent messages that fit a token budget, about 300 tokens here, and drops the rest: 2 of 10 messages kept on Groq, whose answers were longer, and 4 of 10 on Claude. Delete removes chosen messages, here the four long explanations in the middle: 6 of 10 kept, including the first message where the user gave her name. Summarise replaces the six oldest messages with one summary written by the model and keeps the last four: 5 messages, and the summary still names the user.](/images/ai-llms/agentic-ai/how-ai-agents-remember/short-term-strategies.svg)

### The buffer: keep everything

```python title="short_term_memory.ipynb (the buffer)"
message_buffer = []

def chat(user_input):
    message_buffer.append(HumanMessage(content=user_input))
    response = llm.invoke(message_buffer)          # the whole history, every time
    message_buffer.append(response)
    return response.content
```

The conversation: "Hi! My name is Alice and I'm learning about AI", three questions about machine learning, and finally "Thanks! Can you remind me what my name is?". ✅ Both models answered "Alice" from the buffer. Ten messages; the long answers about supervised learning make up most of the tokens.

### Trimming: keep the newest that fit

```python title="short_term_memory.ipynb (trimming)"
trimmed_messages = trim_messages(
    message_buffer,
    max_tokens=300,
    strategy="last",                          # keep the LAST messages, drop the oldest
    token_counter=count_tokens_approximately, # about 4 characters per token
    start_on="human",                         # the kept history must start with a user message
    allow_partial=False,                      # never cut a message in half
)
```

The budget is in (approximate) tokens, which is how models count, and `start_on="human"` matters because chat models expect a conversation to open with a user turn. 📘 Shivank's version replaced the original's home-made character counter with this. ✅ Groq's answers were long, so only the last exchange fitted: 2 of 10 messages. Claude's were shorter: 4 of 10.

The notebook then says, in a markdown cell: *"Trimming removes old messages entirely. Early context (like the user's name) is LOST."* It never asks for the name after trimming. So I did.

![Testing the notebook's claim that trimming loses the user's name. The notebook says so but never asks for the name after trimming. Test A, the notebook's own five-turn chat: the trim keeps the last two messages, and the last answer already says 'Your name is Alice', yet asked again, Claude said it didn't know the name and that its earlier answer had been wrong. Test B, the first four turns only: on Claude the trim kept two messages, neither mentioning Alice, and the model said it didn't know; on Groq a long answer alone was over the 300-token budget and the trim kept no messages at all.](/images/ai-llms/agentic-ai/how-ai-agents-remember/trim-test.svg)

```python title="trim_check.py (my test, same conversation and settings)"
for label, n in [("A: all 5 turns (as in the notebook)", 5), ("B: first 4 turns only", 4)]:
    kept = trim(build(n))
    answer = llm.invoke(kept + [HumanMessage(content="What's my name again?")]).text
```

```text output
A: all 5 turns (as in the notebook): kept 2 messages, 1 of them mention Alice
   answer: I don't know your name. I can't see anywhere in our conversation where you told me, so my earlier answer was wrong. I shouldn't have said "Alice." …
B: first 4 turns only: kept 2 messages, 0 of them mention Alice
   answer: I don't know your name. You haven't mentioned it in our conversation, and I don't have a way to look it up. …
```

✅ That's Claude. On Groq (`gpt-oss-20b`, after the daily quota on the larger model ran out) test A answered simply "You're Alice.", and test B kept **0** messages: an empty history. Three things came out of it:

1. **In the notebook's own conversation the name survives the trim**, because the last turn asked for the name and the answer, "Your name is Alice", is the newest message. The claim is untested, and for this conversation the name is not lost from the text.
2. **Claude still refused it; Groq didn't.** With only "remind me what my name is?" and "Your name is Alice" left, Claude decided its own earlier answer had no support and took it back. Trimming loses *provenance* as well as facts: a claim with no visible source is a claim the model may distrust.
3. **The budget can leave nothing.** In Groq's test B, the newest answer was over 300 tokens on its own, so no run of messages starting with a user turn fitted and `start_on="human"` left an **empty** history; the model was sent the question alone. A fixed token budget must be bigger than the longest message you expect, or trimming silently sends the model nothing.

If a lesson says a technique loses information, ask the question and check.

### Deleting: remove chosen messages

```python title="short_term_memory.ipynb (deletion)"
deleted_buffer = message_buffer[:4] + message_buffer[8:]     # drop messages 4-7, the long explanations
```

✅ Six of ten kept, including the first message with the name, so both models answered "Alice". Deletion keeps what you choose, but these indices only fit this exact conversation; a real agent needs a rule ("drop tool results older than N turns"). Inside a LangGraph agent you delete from the state with `RemoveMessage` and the `add_messages` reducer, which the notebook shows on the same buffer: ✅ "Before: 10 messages / After removing the earliest two: 8 messages".

### Summarising: compress the old part

```python title="short_term_memory.ipynb (summarising)"
summary = summarize_messages(message_buffer[:6], llm)        # one model call
summarized_buffer = [SystemMessage(content=f"Previous conversation summary: {summary}")] + message_buffer[6:]
```

✅ Both summaries began with Alice ("Alice, who is learning about AI…", "Alice introduced herself as a learner of AI…"), so the five-message buffer still answered the name question. Summarising costs a model call and keeps only what the summary chose to keep. The explainer's known limit: summarise a second time and the old summary must be folded into the new one, or earlier facts are lost. 📘

| Strategy | Cost | Keeps the start? | Risk |
| --- | --- | --- | --- |
| Buffer | Grows every turn | Yes | Overflows the context window |
| Trim | Free | No | Loses the start; a small budget can keep nothing |
| Delete | Free | If you choose | Needs a rule for what to delete |
| Summarise | One model call | As a summary | Details the summary dropped are gone |

## Part 2: Saving the conversation with LangGraph and AgentCore Memory

Part 1 decided *what* to keep of one conversation. This part makes the conversation itself survive: the thing that lets an agent answer "what did I just ask you?" after the program has stopped, or from another machine.

This part comes from a second course notebook. A math agent does a multi-step calculation, answers a follow-up question about it, and then shows that a brand-new session starts with a blank slate. Only the agent's model runs on Groq. The memory runs on AWS, so you need AWS credentials but no Bedrock *model* access.

### LangChain, LangGraph and state

The earlier posts used Strands. This part uses **LangChain** and **LangGraph**, so a quick orientation first.

LangChain is an open-source framework for building applications on top of LLMs. It gives you ready-made building blocks, so you don't write the plumbing for each model provider and each tool yourself. It provides:

- **Model wrappers:** one interface for many providers (OpenAI, Anthropic, Groq, Ollama and others). Swapping models means changing one line.
- **Prompts and output parsing:** templates for prompts, and helpers that turn model text into structured data.
- **Tools:** a standard way to give a model functions it can call.
- **Agents:** a loop where the model decides which tool to call, reads the result and continues, the same idea as the Strands loop.
- **Retrieval (RAG):** loaders, text splitters, embeddings and vector store integrations, for answering questions over your own documents.
- **Memory and chat history:** helpers for carrying conversation state.
- **Integrations:** hundreds of third-party connectors, split into separate packages such as `langchain-groq` and `langchain-openai`.

The family of packages:

| Package | Role |
| --- | --- |
| `langchain` | Core agent and chain building blocks |
| `langchain-groq` | Connector that lets LangChain talk to Groq models |
| `langgraph` | Lower-level library for stateful, multi-step agent workflows drawn as a graph of nodes. It also handles branching, loops and multi-agent setups. |
| `langsmith` | Tracing and evaluation, so you can see what an agent did (a separate product) |

**LangGraph** builds agents as a *graph*. Each box in the graph is a step (a node), such as "ask the model" or "run a tool", and the arrows say which step comes next. The agent loop (decide, call a tool, read the result, decide again) is just a graph with a cycle in it.

What travels through the graph is called the **state**. For a chat agent, the state is mostly one thing: the list of messages so far. The helper `langchain.agents.create_agent` builds the graph for you, so you don't have to draw the boxes yourself.

<Callout type="info" title="LangChain versions move fast">

LangChain has changed its API a lot between versions. The notebook pins the 1.x line, so old tutorials written for 0.x often don't run on it. Check the version when you copy code.

</Callout>

### Checkpoints and checkpointers

A **checkpoint** is a snapshot of the state, taken after a step. A **checkpointer** is the component that saves those snapshots and loads them back. Once an agent has one, you get several things almost for free:

- **Continue a conversation:** load the latest checkpoint and carry on.
- **Survive crashes:** if the process dies, resume from the last snapshot.
- **Inspect history:** see how the state looked after each step.

By default a checkpointer can simply keep snapshots in RAM, and they disappear when the program stops. The point of this notebook is to swap in a **durable** one that stores them in the cloud.

![A LangGraph agent: START leads to a model node and a tools node that loop until the model makes no tool call, then END. After every step a snapshot is saved to AgentCore Memory, and the latest state is loaded when a run begins](/images/ai-llms/agentic-ai/how-ai-agents-remember/langgraph-checkpointer.svg)

### Amazon Bedrock AgentCore Memory

**AgentCore Memory** is a managed memory service from AWS, part of Amazon Bedrock AgentCore. You create a *memory resource*, a storage container identified by a `memory_id`, and then read and write to it. It can do two jobs:

- **Short-term:** store the raw sequence of events in a conversation. This is what we use here.
- **Long-term:** extract and keep facts across sessions. This needs *extraction strategies*, which the notebook says aren't needed for short-term memory, so we skip them.

Because the data lives in AWS and not in your notebook's RAM, the agent can pick up where it left off, even from a different process or machine.

### thread_id, session_id and actor_id

AgentCore organises memory with two IDs, and LangGraph has its own name for one of them:

| In LangGraph | In AgentCore | Meaning |
| --- | --- | --- |
| `thread_id` | `session_id` | One conversation. A new value means a fresh conversation. |
| `actor_id` | `actor_id` | Who the conversation belongs to: a user or an agent. |

You pass both in the run config, and both are required. This is the lever that controls what the agent remembers: **same `thread_id`, same conversation; new `thread_id`, blank slate.**

```python
import os  # standard library: read environment variables

# MemoryClient: AWS-side client for managing AgentCore Memory resources

from bedrock_agentcore.memory import MemoryClient

from dotenv import load_dotenv

# (model + tools + loop) as a LangGraph graph
from langchain.agents import create_agent

from langchain.chat_models import init_chat_model

# tool: decorator that turns a Python function into a tool the model can call
from langchain.tools import tool

# AgentCoreMemorySaver: a LangGraph checkpointer that saves checkpoints in
# AgentCore Memory instead of RAM (from the langgraph-checkpoint-aws package)
from langgraph_checkpoint_aws import AgentCoreMemorySaver

load_dotenv()  # reads GROQ_API_KEY from a .env file, if present

# Which Groq model to use. Falls back to gpt-oss-120b if GROQ_MODEL_ID isn't set.
MODEL_ID = os.getenv("GROQ_MODEL_ID", "openai/gpt-oss-120b")

# AgentCore Memory lives in an AWS Region. Look for AWS_REGION first, then
# AWS_DEFAULT_REGION, and use us-east-1 if neither is set.
REGION = os.getenv("AWS_REGION", os.getenv("AWS_DEFAULT_REGION", "us-east-1"))

print(f"Model: {MODEL_ID} | Region: {REGION}")
```

Which pip package each import comes from:

| Import | Pip package | Role |
| --- | --- | --- |
| `bedrock_agentcore` | `bedrock-agentcore` | Talks to AgentCore, including creating memory resources |
| `langgraph_checkpoint_aws` | `langgraph-checkpoint-aws` | The AgentCore-backed checkpointer for LangGraph |
| `langchain` | `langchain` | `create_agent`, `init_chat_model` and `tool` |
| `dotenv` | `python-dotenv` | Loads secrets from a `.env` file |

Nothing here is the model itself. The Groq connector is loaded later, by name, inside `init_chat_model`.

### Create the memory resource

```python
# Admin client for AgentCore Memory, pointed at our Region
client = MemoryClient(region_name=REGION)

# Create the memory the first time; on later runs, find and reuse it.
# It waits until the resource is ACTIVE before returning.
memory = client.create_or_get_memory(
    name="MathLanggraphAgentGroq",
    description="Short-term memory for the LangGraph math agent",
)

# The resource's ID. The checkpointer needs this to know where to save.
memory_id = memory["id"]

# .get() returns None instead of raising an error if "status" is missing
print("Memory ID:", memory_id, "| status:", memory.get("status"))
```

`create_or_get_memory` is *idempotent*: running it twice doesn't create two resources. The first call can take a little while because AWS has to provision the resource, and the call waits for it to become `ACTIVE`. No extraction strategies are configured, so this resource only stores raw conversation events.

### The checkpointer and the model

```python
# The checkpointer: tells LangGraph to save every step into the AgentCore
# Memory resource we just created. Region must match where it lives.
checkpointer = AgentCoreMemorySaver(memory_id, region_name=REGION)

# The model. "groq" picks the Groq connector, MODEL_ID picks the model.
# max_retries=5 retries dropped connections or rate-limit hiccups.
# The key is read from the GROQ_API_KEY environment variable.
llm = init_chat_model(MODEL_ID, model_provider="groq", max_retries=5)
```

This is the cleanest place to see the split: the **model** runs on Groq and the **memory** lives on AWS. Changing one doesn't affect the other.

### Tools and the agent

```python
@tool  # makes this function a tool; the docstring becomes its description
def add(a: int, b: int) -> int:
    """Add two integers and return the result."""
    return a + b


@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers and return the result."""
    return a * b


tools = [add, multiply]  # the list we hand to the agent

graph = create_agent(
    model=llm,          # the Groq model
    tools=tools,        # the tools it may call
    # Tells the model to always use the tools instead of calculating itself
    system_prompt="You are a helpful assistant. Use the tools for every calculation.",
    # The line that adds memory: save and load state through AgentCore
    checkpointer=checkpointer,
)

graph  # in a notebook, the last expression is displayed, here as a diagram
```

`@tool` works the same way as in Strands: the function name, type hints and docstring are all the model sees. Why use tools for arithmetic? Language models are unreliable at multiplying big numbers in their heads, and a function is exact.

The result is called `graph` because that is what it is: a LangGraph graph with a model step, a tool step and the arrows between them. Without `checkpointer=checkpointer` it would still work, but it would forget everything between runs.

### Run it

```python
# The run config. Both IDs are required by the AgentCore checkpointer.
config = {
    "configurable": {
        "thread_id": "session-1",    # maps to AgentCore session_id: one conversation
        "actor_id": "react-agent-1", # maps to AgentCore actor_id: who it belongs to
    }
}

# The input: a list of messages, each with a role and content
inputs = {
    "messages": [
        {"role": "user", "content": "What is 1337 times 515321? Then add 412 and return the value to me."}
    ]
}

# Run the agent and print each step as it happens
for chunk in graph.stream(inputs, stream_mode="updates", config=config):
    print(chunk)
```

`graph.stream` runs the agent and hands you results as they happen, instead of waiting until the end. `stream_mode="updates"` means each `chunk` is only the *change* made by one step, labelled with the name of the step that made it. (A `values` mode also exists, which gives you the full state each time.)

**What to expect:** the question has two parts, and the second depends on the first, so the model can't do them at once.

1. The model asks to call `multiply` with 1337 and 515321.
2. The tool returns 688,984,177.
3. The model asks to call `add` with that result and 412.
4. The tool returns 688,984,589.
5. The model writes the final answer.

Each of those steps is one chunk on the screen, and after each one the checkpointer saves a snapshot to AgentCore. The exact names on the chunks depend on the library version, but they are usually the model step and the tools step.

### Inspect the saved state and its history

```python
# get_state loads the latest checkpoint for this thread from AgentCore
for message in graph.get_state(config).values.get("messages"):
    # message.type tells who wrote it; message.text is the content as a string
    print(f"{message.type}: {message.text}")
    print("=" * 40)  # a separator line
```

This reads the conversation back from AWS, not from your notebook's variables. The `type` is one of a small set: `human` for you, `ai` for the model and `tool` for tool results. For this question, expect about six messages: your question, the model's call to `multiply`, its result, the call to `add`, its result and the final answer. The `ai` messages that call tools may have empty text, since their content is the tool call.

```python
# Every checkpoint saved for this thread, most recent first
for checkpoint in graph.get_state_history(config):
    print(
        # Each checkpoint has its own ID...
        f"Checkpoint {checkpoint.config['configurable']['checkpoint_id']} "
        # ...and its own snapshot of the messages at that moment
        f"— messages in state: {len(checkpoint.values.get('messages', []))}"
    )
```

This is the part that shows what a checkpointer really is. The list starts at the newest checkpoint, with every message, and goes back in time with fewer and fewer messages, until the empty start. Every step in the run left a snapshot behind.

![Seven checkpoint cards from an empty start to the final answer, with the message count growing from 0 to 6. get_state reads the newest one and get_state_history walks back through all of them](/images/ai-llms/agentic-ai/how-ai-agents-remember/checkpoint-timeline.svg)

<Callout type="info" title="Why keep history at all?">

Because snapshots are saved per step, an agent can be resumed from the middle, replayed or rewound to an earlier point. This notebook only reads the history, but the same checkpoints are what make those features possible.

</Callout>

### Continue a session, then start a new one

First, a follow-up in the **same** session. It reuses the same `config`, so the same `thread_id`:

```python
# Same config as before, so the same thread_id: "session-1"
inputs = {"messages": [{"role": "user", "content": "What were the first calculations I asked you to do?"}]}

for chunk in graph.stream(inputs, stream_mode="updates", config=config):
    print(chunk)
```

Nothing in this message mentions the numbers. The agent can answer only because the checkpointer loaded the earlier messages for `session-1` and put them in front of the model. The answer should mention 1337, 515321 and 412. This is short-term memory working.

Then the same kind of question in a **new** session:

```python
# Same actor_id, but a NEW thread_id, so a brand new conversation
config = {
    "configurable": {
        "thread_id": "session-2",     # new session
        "actor_id": "react-agent-1",  # same actor
    }
}

inputs = {"messages": [{"role": "user", "content": "What values did I ask you to multiply and add?"}]}
for chunk in graph.stream(inputs, stream_mode="updates", config=config):
    print(chunk)
```

![Under one actor, session-1 holds the saved messages of the math conversation while session-2 is a new thread with no checkpoints, so a question about the earlier numbers has nothing to draw on](/images/ai-llms/agentic-ai/how-ai-agents-remember/session-isolation.svg)

Now the agent has no history to work from, because `session-2` has no checkpoints. It should say it doesn't know what you mean. The `actor_id` is the same as before and it makes no difference: short-term memory is per *session*, not per actor.

<Callout type="tip" title="Check it doesn't pretend">

A model with no history may still try to be helpful and guess. When you run the isolation test, read the answer carefully: the right result is "I have no record of that", not a made-up calculation.

</Callout>

This cell also *reassigns* the `config` variable. After it runs, `config` points at `session-2`, so if you re-run an earlier cell afterwards, it will quietly use the new session.

```python
# Delete the AgentCore Memory resource and everything stored in it.

client.delete_memory_and_wait(memory_id=memory_id, max_wait=300, poll_interval=10)
```

This deletes the whole resource, including all saved sessions. Next time you run the notebook, `create_or_get_memory` will create a fresh one.

## Things that can trip you up

- **Believing a claim the notebook never tests.** "Trimming loses the name" wasn't checked; in that conversation it doesn't.
- **A token budget smaller than one message.** `trim_messages` with `start_on="human"` can return an empty history. Size the budget for your longest answers.
- **Hard-coded deletion indices.** `[:4] + [8:]` fits one conversation. Use a rule.
- **Summaries that pile up.** Fold the previous summary into the next one.
- **Hot-path extraction saving non-facts.** Extracting from one message at a time saved a question as a fact; batch extraction saw the whole chat and didn't.
- **AWS credentials or permissions missing.** The failure shows up at `create_or_get_memory`. Check your credentials and the IAM permissions listed above.
- **Region mismatch.** The memory resource lives in one Region. Use the same `REGION` for the client and the checkpointer.
- **Forgetting `thread_id` or `actor_id`.** Both are required by the AgentCore checkpointer.
- **Groq rate limits.** On a free tier, expect HTTP 429s, per minute and per day. `max_retries` helps with the first kind only.
- **Leaving the AWS resource behind.** If the notebook stops before the last cell, delete the memory resource yourself.

## What I learned

Short-term memory is not a feature you switch on; it is the transcript you decide to resend. Every strategy is a trade between cost, what survives, and how much work it takes to choose. And the tests in a lesson are worth re-running with one more question: the notebook's own conversation contradicted its own note.

## What I'd do differently

Write the recall question into every memory experiment: after any trim, delete or summary, ask for the one fact that matters and print the answer. That single line would have caught the untested claim and the empty-history case at once.

## Summary

A model call keeps nothing, so memory is the app resending the right text. Decide what to keep, when to write it, where to store it, how to find it and how much to keep; writing in the hot path is fresh but slow, in the background fast but late. One conversation can be kept small by trimming, deleting or summarising, each losing something different, and the claims about what is lost are worth testing. A checkpointer then saves the conversation after every step so it survives the process, keyed by thread; AgentCore Memory keeps those snapshots in AWS.

### Concepts at a glance

| Term | In one line |
| --- | --- |
| **Stateless** | A model call keeps nothing between requests |
| **Context window** | The most text a model can read in one call |
| **Hot path / background** | Write memory before replying, or later in a batch |
| **Buffer** | The whole message history, resent every turn |
| **Trimming** | Keep only the newest messages that fit a token budget |
| **Deleting** | Remove chosen messages; `RemoveMessage` inside LangGraph |
| **Summarising** | Replace old messages with a model-written summary |
| **Checkpoint / checkpointer** | A snapshot of the state after a step / what saves and loads them |
| **`thread_id`** | Which conversation a checkpoint belongs to |

### Test yourself

<details>
<summary>If the model is stateless, how does a chatbot "remember" what you said earlier?</summary>

The app resends the earlier messages with every request. Memory is what the app chooses to put back into the prompt.

</details>

<details>
<summary>When would you write memory in the background instead of the hot path?</summary>

When reply speed matters more than having a new fact available instantly in other conversations. The current conversation still has the fact in its own history either way.

</details>

<details>
<summary>The notebook trims to 300 tokens with start_on="human". How can that send the model an empty history?</summary>

If the newest message alone is longer than 300 tokens, no run of messages that starts with a user message fits, so nothing is kept.

</details>

<details>
<summary>After trimming, the history still said "Your name is Alice", but the model said it didn't know. Why?</summary>

Only the model's own earlier answer remained; nothing the user said supported it, so the model treated it as unsupported. Trimming loses where a fact came from, not only the fact.

</details>

<details>
<summary>What identifies a conversation to the checkpointer?</summary>

The `thread_id` in the config. With AgentCore Memory, `actor_id` is required too.

</details>
