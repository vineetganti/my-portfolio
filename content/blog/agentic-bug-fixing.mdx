You give this agent a Python function and the inputs that make it crash. It runs the function, sees the crash, and asks an LLM to rewrite the function so it handles that error. Then it loads the rewrite, runs it again, and stops when it works or after three tries. The design is two nodes and a router, which is about the smallest program that still behaves like a coding agent.

The agent, its code and the walkthrough this post leans on are by **Shivank Agarwal** ([Future with Shivank](https://www.linkedin.com/in/shivankagrawal/)), from his AI Bootcamp at **Scaler Academy**, the course this whole series follows. All credit for the design, the code and the teaching material goes to them. Shivank's explainer covers an OpenAI version. I ported it back to Groq, packaged it, and published my copy at [github.com/vineetganti/agentic-bug-fixing](https://github.com/vineetganti/agentic-bug-fixing). The repo's LICENSE file is a credit notice for Future with Shivank and Scaler. It isn't an open-source licence.

As in the rest of the series, most of what I learned came from things going wrong, and this post keeps every one of them. The bugs I found are now fixed in the repo, and each one is shown before and after.

<Callout type="note" title="TL;DR">

- **What it does:** a LangGraph graph with two nodes, `code_execution_node` (run it) and `code_fix_node` (ask the LLM for a rewrite and load it). A router sends a crash to the fix node and a success to the end, and it stops after `MAX_FIX_ATTEMPTS = 3`.
- **Bug 1, the model:** the course's model, `llama-3.3-70b-versatile`, returned a **404**. Groq had shut it down on 16 August 2026. Claude Code listed the models my key could use and switched to `openai/gpt-oss-120b`.
- **Bug 2, the stray bracket:** about **3 replies in 10** ended the fix with an extra `)`, which is a `SyntaxError`. The retry sent the *same* prompt, so **4 of 13 retries failed again**, and one run gave up after three tries. When I sent the load error back with the next request, **6 of 6 retries worked**. That change is now in the repo, and in 24 more runs **4 of 4 retries loaded** and none gave up.
- **The brake, measured:** without it, a model that keeps failing loops **5,003 times** before LangGraph stops it. LangGraph's default limit is now 10,007 steps.
- **Smaller bugs:** when the agent gave up, the demo said "(no fix was needed)" and the app showed a green "No errors detected". The project's `.venv` didn't have the Groq client. And in dark mode, the app's diff lost every line except the added ones. All of these are fixed in the repo now.

</Callout>

## The goal: an agent that repairs crashing functions

Here's the whole idea in one function:

```python title="the running example"
def divide_two_numbers(a, b):
    return a / b          # divide_two_numbers(10, 0) -> ZeroDivisionError
```

The agent runs it with `[10, 0]` and it crashes with `ZeroDivisionError: division by zero`. The agent then sends the model the code, the arguments and the error, and asks for a version that "handles this error gracefully by returning an error message (a string) instead of crashing". It loads the rewrite, runs it again, and gets `'Error: division by zero'`. If the rewrite still crashes, it goes round again with the newest code, at most three times.

<Callout type="analogy" title="The mechanic's test drive (Shivank's analogy)">

A mechanic test-drives the car (**run**). If there's a strange noise, they fix it (**ask the LLM**) and drive again. After three failed attempts they stop and call the customer, instead of working on it for ever. Fix, re-test, stop after N tries: that loop is the heart of most coding agents.

</Callout>

![The agent's graph. START leads to code_execution_node, which runs the function and records the result or the error. The error_router then decides: if the run worked, or three fix attempts have been used, it goes to END. If the function crashed, it goes to code_fix_node, which asks the LLM for a rewrite and loads the new code, and an edge always leads back to code_execution_node to run the new version. ### Agent or workflow?

Anthropic's [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) separates two kinds of system. **Workflows** are "systems where LLMs and tools are orchestrated through predefined code paths". **Agents** are systems where "LLMs dynamically direct their own processes and tool usage".

By those definitions, this program is a **workflow**. The model never picks the next step: the graph and the router do. The model only decides what code to write. The shape it follows is the one Anthropic calls **evaluator-optimizer**, where "one LLM call generates a response while another provides evaluation and feedback in a loop". Here the evaluator isn't an LLM at all. It's the Python interpreter, which either runs the code or raises an exception. That's a cheap, strict and honest judge, and it's why the same article notes that "code solutions are verifiable through automated tests".

## Part 2: The code, step by step

### Step 0: imports and settings

- `MAX_FIX_ATTEMPTS` is the brake. Part 4 measures what it's worth.

### Step 1: the State, a shared job card

```python title="agentic_bug_fixing/agent.py · lines 69–79"
class State(BaseModel):
    function: Callable              # the actual Python function object we will run
    function_string: str            # the ORIGINAL source code, as text
    arguments: list                 # inputs to call the function with, e.g. [10, 0]
    error: bool = False             # did the last run crash?
    error_description: str = ""     # the crash message, e.g. "ZeroDivisionError: division by zero"
    new_function_string: str = ""   # the fixed code written by the LLM ("" = no fix needed)
    attempts: int = 0               # how many times we have asked the LLM to fix it
    load_error: str = ""            # why the LLM's last rewrite would not load, e.g. "SyntaxError: ..."
    bad_reply: str = ""             # that rewrite, so the next request can show the LLM its mistake
    result: Any = None              # what the function returned on its last good run
```

The State is everything the agent knows right now. It holds the function twice, on purpose. `function` is the object Python runs, and `function_string` is the text the model reads. `load_error` and `bad_reply` are new: they carry a rewrite that wouldn't load into the next request (bug 2). The comment on `new_function_string` says `""` means "no fix needed", which isn't true when the agent gives up, so the demo and the app now check `error` first (bug 3).

LangGraph's docs describe how the State changes: "Nodes return partial updates. LangGraph applies those updates through each channel's reducer", and with no reducer, updates simply overwrite ([Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)). So a node returns a small dict of the fields it changed, never the whole State. A Pydantic model is allowed "when you need validation". The same page says to "Prefer `TypedDict` or `dataclass` for performance", but for a demo, getting a loud error on a typo like `state.erorr` is worth it.

### Step 3: turning LLM text into running code

```python title="agentic_bug_fixing/agent.py · lines 104–111"
def clean_llm_code(text: str) -> str:
    """the LLM sometimes wraps code in ```python ... ``` even when told not to. Remove that."""
    text = text.strip()
    fenced = re.search(r"```(?:python|py)?[ \t]*\n(.*?)```", text, re.DOTALL)
    if fenced:
        text = fenced.group(1)
    # dedent: if the code arrives indented, exec() would fail with "unexpected indent"
    return textwrap.dedent(text).strip()
```

If the reply contains a fenced block, keep only what's inside it. Then [`textwrap.dedent`](https://docs.python.org/3/library/textwrap.html#textwrap.dedent) will "Remove any common leading whitespace from every line in text." I fed it a chatty, fenced reply to check:

```text output title="✅ re-run: clean_llm_code on a fenced reply"
in:  'Sure! Here is the fix:\n```python\ndef f(x):\n    return x\n```\nHope this helps.'
out: 'def f(x):\n    return x'
```

```python title="agentic_bug_fixing/agent.py · lines 114–135"
def first_function_name(code: str) -> str:
    tree = ast.parse(code)
    for node in tree.body:
        if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef)):
            return node.name
    raise ValueError("No function definition (def ...) found in the code.")


def load_function_from_code(code: str, function_name: str | None = None) -> Callable:
    namespace: dict = {}
    exec(code, namespace)  # <-- runs the LLM-written code: see the SAFETY NOTE at the top
    name = function_name or first_function_name(code)
    function = namespace.get(name)
    if not callable(function):
        raise ValueError(f"The code does not define a function called '{name}'.")
    return function
```

[`ast.parse`](https://docs.python.org/3/library/ast.html#ast.parse) reads code the way Python does, into "a tree of objects whose classes all inherit from ast.AST", without running it. That's a safe way to find the first `def`. `exec()` is the opposite: it **runs** the text. Running a `def` doesn't call the function. It creates it and stores it in the `namespace` dictionary, where the code picks it up by name. Python's docs put the risk bluntly: "This function executes arbitrary code. Calling it with untrusted user-supplied input will lead to security vulnerabilities" ([`exec`](https://docs.python.org/3/library/functions.html#exec)). The model's reply is exactly that kind of input. Every `SyntaxError` in this post was raised on this line.

**Node 1** runs the function and records what happened:

```python title="agentic_bug_fixing/agent.py · lines 148–158"
    def code_execution_node(self, state: State) -> dict:
        print(f"[run]  {state.function.__name__}{tuple(state.arguments)}")
        try:
            result = state.function(*state.arguments)
        except Exception as e:
            # Keep the error TYPE too: "KeyError: 'INVALID'" tells the LLM far more than "'INVALID'"
            description = f"{type(e).__name__}: {e}"
            print(f"[run]  crashed -> {description}")
            return {"error": True, "error_description": description}
        print(f"[run]  ok -> {result!r}")
        return {"error": False, "error_description": "", "result": result}
```

`*state.arguments` unpacks `[10, 0]` into `(10, 0)`. The node returns only the fields it changed. Because the `try`/`except` is here, a crash becomes *data in the State*, not an exception that ends the program.

**Node 2** asks the model:

```python title="agentic_bug_fixing/agent.py · lines 162–195"
    def code_fix_node(self, state: State) -> dict:
        attempt = state.attempts + 1
        print(f"[fix]  attempt {attempt}/{MAX_FIX_ATTEMPTS}: asking {self.llm.model_name} to fix it")

        # If an earlier fix still crashed, send the LATEST code, not the original one.
        code_to_fix = state.new_function_string or state.function_string

        # If the LLM's last rewrite would not even load, tell it why and show it what it sent.
        # Without this, a retry sends the exact same prompt and can get the exact same mistake back.
        feedback = ""
        if state.load_error:
            feedback = (f"Your previous rewrite could not be loaded by Python ({state.load_error}). "
                        f"This is what you sent:\n{state.bad_reply}\n\n")

        reply = self.fix_chain.invoke({
            "function_string": code_to_fix,
            "arguments": json.dumps(state.arguments, default=str),
            "error_description": state.error_description,
            "feedback": feedback,
        })
        new_code = clean_llm_code(reply.content)

        try:
            new_function = load_function_from_code(new_code, state.function.__name__)
        except Exception as e:
            # The LLM wrote code that doesn't even load. Count the attempt, keep the previous
            # version, and remember the error and the reply so the next request can show them.
            load_error = f"{type(e).__name__}: {e}"
            print(f"[fix]  the new code could not be loaded ({load_error})")
            return {"attempts": attempt, "load_error": load_error, "bad_reply": new_code}

        print("[fix]  new version loaded, running it again")
        return {"attempts": attempt, "function": new_function, "new_function_string": new_code,
                "load_error": "", "bad_reply": ""}
```

`self.fix_chain.invoke(...)` is the only line that talks to the network. Look closely at the `except` branch. When a reply won't load, it saves the error and the broken code in the State, and the next request shows them to the model through `{feedback}`. Before the fix, that branch returned only `{"attempts": attempt}`: the broken reply and the `SyntaxError` were printed, then **thrown away**, and the next attempt rebuilt exactly the same prompt. Part 4 shows what that cost.

**The router** decides, and changes nothing:

```python title="agentic_bug_fixing/agent.py · lines 198–204"
    def error_router(self, state: State) -> str:
        if not state.error:
            return END                                  # it worked, we're done
        if state.attempts >= MAX_FIX_ATTEMPTS:
            print(f"[stop] still failing after {state.attempts} fix attempts, giving up")
            return END                                  # safety brake
        return "code_fix_node"                          # crashed: go fix it
```

**Wiring:**

```python title="agentic_bug_fixing/agent.py · lines 207–217"
    def build_graph(self):
        builder = StateGraph(State)
        builder.add_node("code_execution_node", self.code_execution_node)
        builder.add_node("code_fix_node", self.code_fix_node)

        builder.set_entry_point("code_execution_node")                 # always start by running it
        # then ask the router; naming where it can go lets get_graph().draw_mermaid() draw the loop
        builder.add_conditional_edges("code_execution_node", self.error_router, ["code_fix_node", END])
        builder.add_edge("code_fix_node", "code_execution_node")       # after a fix, run again

        return builder.compile()
```

| Line | Meaning |
| --- | --- |
| `StateGraph(State)` | This graph passes a `State` around |
| `add_node(name, function)` | Register a step |
| `set_entry_point(...)` | Always start by running the code |
| `add_conditional_edges(node, router, [...])` | After running, ask the router. The docs: "If you want to optionally route to one or more nodes (or terminate), use `add_conditional_edges`". The list of places it can go was added as a fix, so the graph can be drawn (Part 3) |
| `add_edge(fix, execution)` | After every fix, always run again. **This edge makes the loop** |
| `compile()` | Check the wiring and return a runnable graph |

Finally, `run()` builds the starting State, getting the function's text with `textwrap.dedent(inspect.getsource(function))` (lines 220–227). [`inspect.getsource`](https://docs.python.org/3/library/inspect.html#inspect.getsource) will "Return the text of the source code for an object", including its indentation. The demo's function is defined *inside* another function, so its text arrives indented:

### The brake, measured

How much is `MAX_FIX_ATTEMPTS = 3` worth? I used the same stand-in, which never produces a working fix, and set the limit to three and then to a million:

```text output title="✅ re-run: nokey_checks.py, no API calls"
MAX_FIX_ATTEMPTS=3: stopped, attempts=3, error=True
MAX_FIX_ATTEMPTS=1000000: GraphRecursionError after 5003 fix attempts: Recursion limit of 10007 reached without hitting a stop condition. You can increase the limit by setting the `recursion_limit` config key.
```

Without the brake, the only thing that stopped the loop was LangGraph's recursion limit, which "caps how many super-steps one run may execute". Since version 1.1.4 "the default is 10,007 super-steps" ([Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)). Each lap is two steps, a fix and a run, so that's **5,003 calls to the model** before the error. If you remember the limit as 25, that's `langchain-core`'s default (`DEFAULT_RECURSION_LIMIT = 25` in `langchain_core/runnables/config.py`), which LangGraph replaces with its own. Anthropic's advice to "include stopping conditions (such as a maximum number of iterations) to maintain control" is about exactly this. LangGraph's limit protects against infinite loops. It doesn't protect your bill.

![Before and after for the attempt limit, run with a stand-in model that always returns the broken reply, so no API calls. Before: with the limit set to a million, the agent made 5,003 fix attempts, one LLM call each with a real model, and stopped only when LangGraph raised GraphRecursionError at its default limit of 10,007 steps. After: with MAX_FIX_ATTEMPTS at 3, it stopped after three attempts and returned the State with error set to True, so the caller decides what to do](/images/ai-llms/agentic-ai/agentic-bug-fixing/bug-no-brake.svg)

One of Shivank's changes protects the same loop from a different failure. In the course original, the fix node ran the new function itself, so a second crash escaped the graph. This one is 📘: I'm describing it from his table, not re-running it.

![Before and after for one of Shivank's changes, from his explainer. | Example | Error sent to the model | Tries | What the fix did | Result |

Each model call took between 0.8 and 3.4 seconds. Three lessons stand out, and the first two are Shivank's.

<Callout type="warn" title="The silent bug">

The inventory example returns `None` instead of a stock count. That's wrong, but nothing crashes, so the agent reports "no errors". **This agent can only fix bugs that raise exceptions.** To catch a silent bug you need expected outputs, which means tests. That's why real coding agents run test suites, not just the code.

</Callout>

<Callout type="warn" title="Fixed isn't the same as correct">

The prompt asks for "an error message (a string) instead of crashing". So `calculate_total_price` now returns a number on success and a sentence on failure, and any caller that adds up totals will break later and somewhere else. The agent did what the prompt said, which means the prompt carries your engineering decisions: raise a clear error, return `None`, or log it and alert someone.

</Callout>

The third lesson is mine. The explainer says a sharp fix to the e-commerce example "also notices `margin` is never used". In my single run of each, `gpt-oss-120b` didn't do that, in either example with a dead line. It kept the useless division and wrapped it in `try`. That's the smallest change that stops the crash, and the prompt never asked for more.

## Safety: this runs AI-written code

`exec()` runs whatever text it's given, with your permissions. It could delete files, read `.env`, or call the internet. For toy functions in a demo, that's acceptable. For anything real, Anthropic's advice is "extensive testing in sandboxed environments, along with the appropriate guardrails": a container or VM with no secrets, no network and a time limit. The app is also an open door. In Shivank's words, "anyone who can open it can run code on your machine, so don't share its link publicly."

## What I learned

- **A retry is only as good as the new information it carries.** The loop retried the same prompt and got the same broken reply 4 times in 13. Sending the error back fixed 10 of 10. Claude Code did the same thing with the 404: it listed the models before trying again.
- **Bring your own brake.** LangGraph's limit is 10,007 steps, which stops an infinite loop but not a bill. Three attempts is a product decision. The framework won't make it for you.
- **An LLM's reply is untrusted text.** It needs fence stripping, dedenting and an `ast` parse before it runs. `exec` is the point where text becomes power, so it belongs in a sandbox.
- **Errors should become State, not exceptions.** Catching the crash in the run node, and keeping the error's *type* (`KeyError: 'INVALID'`), is what lets a loop reason about failure at all.
- **"Agent" covers a range.** This is a fixed graph where the code chooses the path, which Anthropic would call a workflow. That's no criticism. It's a big part of why it's predictable enough to teach.
- **A model name is a dependency, and it can be retired.** The setup check's one test call found that in seconds, before the demo ran.
- **Honest output matters.** A run that gave up shouldn't say "no fix was needed", and a diff shouldn't depend on the reader's theme.
- **Check a fix the way the bug was found.** My first dark-mode fix was correct CSS and changed nothing, because a theme rule coloured every element. Only a new screenshot showed it.

## What I'd do differently

- Print the model's raw reply whenever a fix won't load. I needed a wrapper to see a single character. The fixed repo sends it back to the model, but still doesn't print it.
- Create and activate the venv **before** asking an agent to install anything, and check `sys.prefix`.
- Take a new screenshot after every UI fix, instead of trusting the code change.
- Parse each reply with `ast.parse` before `exec`, so a syntax error is caught without running anything.
- Try Shivank's harder exercises next: cache fixes by a hash of the code and error, log tokens per fix, and add expected outputs so the silent bug gets caught.

## Summary

The agent is two LangGraph nodes and a router. One node runs the function and turns a crash into State, and the other sends the code, the arguments and the error to an LLM, then loads the rewrite with `exec`. The router sends a crash to the fix node and stops on success or after three attempts. I took Shivank Agarwal's OpenAI version (Future with Shivank, for Scaler Academy) back to Groq. The course's model had been shut down, so Claude Code listed the models the key could use and picked `openai/gpt-oss-120b`. That model's replies ended with a stray `)` about 3 times in 10. Because the loop throws the bad reply away and resends the same prompt, retries failed again 4 times in 13, and one run gave up. Sending the error back made 10 of 10 retries load, first in an experiment and then in the fixed repo. The brake earns its place: without it, a hopeless loop makes 5,003 calls before LangGraph's 10,007-step limit stops it. The smaller bugs were about honesty and environment: a give-up shown as "no fix needed", two Pythons with one stale venv, and a diff that disappeared in dark mode. All of them are fixed now: a retry carries the load error (4 of 4 loaded in 24 runs), a give-up says so, the diff sets its own colours, the graph draws its loop, and the venv has its packages.

### Test yourself

<details>
<summary>In the log, attempts 1 and 2 failed with the same SyntaxError. Why did attempt 2 so often fail in exactly the same way?</summary>

In the published version, when a reply wouldn't load, `code_fix_node` returned only `{"attempts": attempt}`. The broken reply and the error were thrown away, `new_function_string` stayed empty, and the next run crashed the same way. So attempt 2 built the identical prompt from the same original code and the same `ZeroDivisionError`, and the model can produce the same reply. In my runs, 4 of 13 such retries failed again. Sending the load error and the bad reply back made 6 of 6 retries load in an experiment. The fixed repo keeps both in the State and sends them with the next request: in 24 runs, 4 of 4 retries loaded.

</details>

<details>
<summary>Remove MAX_FIX_ATTEMPTS and give the agent a model that never writes loadable code. What stops it, and after how many model calls (LangGraph 1.2.22)?</summary>

LangGraph's recursion limit, with a `GraphRecursionError`. The default is 10,007 super-steps, and each lap is two steps (fix, then run), so it makes 5,003 fix attempts, each one a model call, before stopping. The brake of 3 stops it after three.

</details>

<details>
<summary>The inventory example returns None for a missing SKU, and the agent says "no errors". Why, and what would catch it?</summary>

`inventory.get(sku)` returns `None` without raising, so `code_execution_node` records `error=False` and the router goes straight to `END`. The agent only sees exceptions. To catch a wrong answer, you need an expected output (a test) and a run node that treats "result ≠ expected" as an error.

</details>

<details>
<summary>One run printed "(no fix was needed)" just above "Still failing". Which State fields explain it?</summary>

`error` was `True` (the last run still crashed) and `attempts` was 3, but `new_function_string` was `""`, because no reply ever loaded, so none was saved. The demo printed "(no fix was needed)" whenever `new_function_string` was empty. The fixed version checks `error` first and says that no rewrite loaded.

</details>

<details>
<summary>Is this program an agent or a workflow by Anthropic's definitions, and which pattern does it follow?</summary>

A workflow. The paths are fixed in code, and the model only writes the function and never chooses the next step. The pattern is evaluator-optimizer: one step generates (the LLM) and another evaluates (here the Python interpreter, by running the code), in a loop with a stopping condition.

</details>
