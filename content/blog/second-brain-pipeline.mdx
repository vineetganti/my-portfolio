## TL;DR

- **Goal:** a daily reading feed from newsletters and engineering blogs, triaged by a language model, curated by me, published to this site with nothing private leaking.
- **Shape:** sources (Gmail through an allowlist, 60+ feeds, watched pages, PDFs, SEC filings) → parse and unwrap links → triage with `claude -p` → SQLite → a local rating page → `nb publish` signs five files → upload → the site verifies them.
- **The model never gets tools or secrets.** Each document goes in on stdin to `claude -p` with all tools disabled, in an empty folder, with a JSON schema; code then drops any link the document didn't contain. 📜 A planted prompt-injection payload had no effect in the one test run.
- **The biggest lessons came from failures:** a Gmail 403 at exactly the quota's limit, a global `pip install` that broke another tool, relevance scores that moved between identical runs, a Save that passed every test and failed for me, and a CI run that broke every signature by changing line endings.
- ✅ Today: 138 Python tests and 13 Node tests pass, and the public-safety check passes on 702 tracked files.

## The goal, and how the work was done

It started as a plan for a newsletter brief: Gmail → parse → deduplicate → summarise with a language model → approve → save to Notion. Twelve days later it had become a different thing: a reading feed for this site, fed by dozens of sources, with the model doing triage and me doing the choosing.

### The agent loop, as the log shows it

![The working loop behind this project, as the build log shows it. The owner asks for something in the chat. Claude Code, the agent, reads files, runs commands and edits code through tools, and each tool result goes back into its context before the next step. Some actions need the owner: running live Gmail fetches, approving installs into the global Python, and making the signing key. The loop ends with tests run and an entry written to the build log.](/images/build-logs/building-this-site/second-brain-pipeline/agent-loop.svg)

[Claude Code](https://code.claude.com/docs/en/overview) is an agent: a model that works through tools. Its documentation describes [the agentic loop](https://code.claude.com/docs/en/how-claude-code-works) as three blended phases, gathering context, taking action and verifying results, with tools used throughout: reading files, searching, editing, running commands. The log shows that loop on almost every page. A typical step: I ask for a feature; Claude Code reads the relevant files, writes code, runs `pytest`, reads the result, fixes what failed, and writes the build-log entry.

Three things the log shows about working this way:

- **Permissions were real decisions.** 📜 Claude Code wrote `fetch_emails()` but did **not** run the live fetch, because that would have pulled my private mail into its context; I ran it and pasted what was needed. Changes to my global Python, outside the project, were made only after I approved them.
- **Tool results feed the next step, including wrong ones.** Several entries record Claude Code noticing that one of its own edits hadn't applied, because the next output lacked something it expected. A loop that verifies its own actions catches its own mistakes; a loop that doesn't, compounds them.
- **Context is finite.** 📘 The context window holds the conversation, file contents and command outputs, and Claude Code [compacts it automatically](https://code.claude.com/docs/en/how-claude-code-works) when it fills, which can lose early detail. 📜 When I asked whether compaction loses data, the answer recorded in entry 21 was: the full transcript stays on disk, but the live working detail can be summarised away. That is exactly why the build log existed: decisions written down survive compaction.

## Setup: two dead ends before any code ran

### A package Python couldn't find

📜 The first command failed:

```powershell title="Command"
python scripts/auth_gmail.py
```

```text title="Output"
Traceback (most recent call last):
  File "<project-root>\scripts\auth_gmail.py", line 2, in <module>
    from newsletter_brief.ingest.auth import gmail_service
ModuleNotFoundError: No module named 'newsletter_brief'
```

I tried running it from inside `scripts/`, with the same result. **Root cause:** the code lives in a `src/` layout and the package wasn't installed. Python imports from the script's own folder and from installed packages, and neither contained `newsletter_brief`, so changing directory couldn't help. **Fix:** an [editable install](https://pip.pypa.io/en/stable/topics/local-project-installs/), `python -m pip install -e ".[dev]"`, which links the installed package to `src/` so edits take effect without reinstalling. `python -m pip` rather than `pip` guarantees the install goes to the same interpreter that runs the script.

### The install that broke another tool

That fixed the import, but the full pip output, pasted later, showed where it had gone:

```text title="Output (📜, abridged)"
Defaulting to user installation because normal site-packages is not writeable
...
ERROR: pip's dependency resolver does not currently take into account all the packages that are installed...
aws-sam-cli 1.171.0 requires click==8.1.8, but you have click 8.5.0 which is incompatible.
aws-sam-cli 1.171.0 requires tomlkit==0.15.1, but you have tomlkit 0.14.0 which is incompatible.
aws-sam-cli 1.171.0 requires watchdog==4.0.2, but you have watchdog 6.0.0 which is incompatible.
```

Line by line: "Defaulting to user installation" means no virtual environment was active, so the project went into the **global** Python's [user site](https://pip.pypa.io/en/stable/user_guide/#user-installs). The `ERROR` lines are pip reporting that it upgraded packages another tool, AWS's SAM CLI, had pinned. Labelled `ERROR`, but the install completed, so in effect it was a warning.

Was SAM actually broken? Claude Code tested rather than assumed: `sam --version` still worked, several `--help` pages worked, and `sam local invoke --help` crashed:

```text title="Output (📜, traceback tail)"
  File ".../site-packages/click/core.py", line 2425, in make_metavar
    metavar = self.type.get_metavar(param=self, ctx=ctx)
TypeError: HiddenChoice.get_metavar() got an unexpected keyword argument 'ctx'
```

The newer `click` passes a `ctx` argument that SAM's own subclass doesn't accept, which is exactly why SAM pins the old version. Pinning it back, with my approval, fixed SAM and immediately broke the pins of other tools:

| Package | SAM wants | Another tool wants | Result |
| --- | --- | --- | --- |
| click | `==8.1.8` | huggingface-hub `>=8.4.2` | one of them is always unhappy |
| tomlkit | `==0.15.1` | gradio `<0.15` | same |
| watchdog | `==4.0.2` | strands-agents `>=6` | no version satisfies both |

That table is the real argument for [virtual environments](https://docs.python.org/3/library/venv.html): in one shared environment, tools with exact pins pull against each other forever. The project moved to its own `.venv`, and later entries record running everything with `.venv\Scripts\python.exe` so the global environment was never touched again. A second oddity, a malformed `-m python -m pip` command my editor had inserted, failed harmlessly and is in the log as an unexplained anomaly.

## Build: ingesting mail

### Gmail's per-minute quota

![The first real failure, before and after. Before: the fetch asked Gmail for every email from the last day and fetched each one in full, back to back. A full fetch costs 60 quota units and the limit is 6,000 units per user per minute, so the run hit 403 rateLimitExceeded after 103 messages. After: a sender allowlist narrows the search at Gmail, each fetch is followed by a 0.7-second pause, about 5,100 units a minute, and a rate-limit error is retried with exponential backoff and jitter.](/images/build-logs/building-this-site/second-brain-pipeline/quota-before-after.svg)

OAuth worked, with a read-only Gmail scope chosen so the code could never send or delete mail ([Google's guide for installed apps](https://developers.google.com/identity/protocols/oauth2/native-app) explains the browser flow, the local redirect and PKCE that the log's first auth URL showed). The first real fetch failed:

```text title="Output (📜, abridged)"
googleapiclient.errors.HttpError: <HttpError 403 ... returned "Quota exceeded for quota metric
'Total Query Cost' and limit 'Units per minute per user' of service 'gmail.googleapis.com' ...".
Details: "[{... 'domain': 'usageLimits', 'reason': 'rateLimitExceeded'}]">
```

A 403 usually means "not allowed", but `reason: rateLimitExceeded` with `domain: usageLimits` means quota, not permission (a missing scope would say `insufficientPermissions`). The numbers, checked against [Gmail's usage limits](https://developers.google.com/workspace/gmail/api/reference/quota): 6,000 quota units per user per minute, and a `messages.get` with `format="full"` costs 60. That is a ceiling of 100 full messages a minute. The run had cached **103** messages when it stopped: consistent with the ceiling, though not a proof, since the window is rolling and the timing wasn't measured.

The root cause was the query, not the speed: `newer_than:1d` matched my whole inbox, receipts and all. Three fixes, cheapest first:

1. **A sender allowlist** that goes into the Gmail search itself (`from:(… OR …)`), so Gmail filters before anything is fetched. An empty allowlist raises an error instead of quietly fetching everything: fail closed. 📜 The next 7-day fetch returned 11 newsletters instead of about 120 mixed emails a day.
2. **A 0.7-second pause** after each uncached fetch: 60 units every 0.7 s is about 5,100 units a minute, under the limit.
3. **Exponential backoff with jitter** for a 429 or a rate-limit 403, as [Google's error guide](https://developers.google.com/workspace/gmail/api/guides/handle-errors) recommends, and an immediate failure for any other 403.

Every fetched message is also saved under `data/raw/`, so the 103 messages fetched before the crash weren't wasted and the parser could be developed offline. `data/` is git-ignored, which matters for private mail.

### Links that hide where they go

📜 Grouped: the HTML-to-text parser and link extractor took several small fixes (a list bullet that landed on the wrong line because of BeautifulSoup's insert order; a `Today�s` that turned out to be the Windows console, not the data). The interesting problem was the links.

Parsing all 180 cached newsletters found **5,318 links**, and 77% of them were TLDR's click-tracking wrappers. Others came from Substack, the New York Times, SendGrid and more. Two consequences:

- **The content filter was blind.** Social links and unsubscribe links hidden behind a tracker looked like content, so the filter kept them. Links have to be **resolved before they are filtered**.
- **Most could be resolved offline.** TLDR's wrapper, and one other kind, carry the real URL, URL-encoded, inside the link. Decoding it needs no network request and clicks nothing.

For the opaque wrappers, a network resolver was built with safety rules as its design, because opening a newsletter link can have side effects (an unsubscribe link may unsubscribe you):

- never request a link whose text says unsubscribe, preferences or view in browser;
- request only known click-tracker hosts; the first redirect that points anywhere else is the answer, and **the destination site is never contacted**;
- follow redirects by hand, `HEAD` first, no cookies, an identifying User-Agent, a pause between requests, at most 8 hops;
- cache answers in SQLite, but never cache network errors.

The live test found three bugs, each kept in the log:

| What happened | Cause | Fix |
| --- | --- | --- |
| A test failed | The test encoded `https%3A%2F%2F`; real links use `https:%2F%2F`. The test was wrong | Accept both |
| A crash on a real link: `httpx.InvalidURL` | A tracker returned a malformed `Location`, and [`InvalidURL` isn't a subclass of `HTTPError`](https://www.python-httpx.org/exceptions/), so the handler missed it | Catch it, and cache it as a refusal |
| NYT links "resolved" to another tracker | NYT hops through a second tracking host that wasn't on the list, so the resolver took it as the destination and cached the wrong answer | Add the host, and ignore any cached answer that is itself a tracker |

📜 On the first TLDR issue, offline only: 16,199 characters of text and 31 links became 9,315 characters and 16 links.

## Build: a language model with no tools

### Using `claude -p` safely

![How an untrusted newsletter reaches the model. The document goes in on stdin, never on the command line. claude -p runs in an empty throwaway folder with all tools disabled, no settings, no MCP servers and no session saved. The output must match a JSON schema. API keys are removed from the environment so the subscription is used. Code then drops any item whose URL was not in the document. In the live test, a planted instruction to create a file and add a fake item had no effect.](/images/build-logs/building-this-site/second-brain-pipeline/triage-sandbox.svg)

I wanted the triage to run on my Claude subscription rather than a paid API key, so the pipeline calls Claude Code's [headless mode](https://code.claude.com/docs/en/headless), `claude -p`, as a plain function: text in, JSON out. That makes it a single model call, **not** an agent: the point is to take the agent's tools away.

📜 Before building, Claude Code checked the real CLI instead of search results. The `claude` binary wasn't on the PATH; the only copy was the one bundled with the VS Code extension, in a versioned folder that changes on every update. The flags came from `--help` on that binary, and the backend ended up as:

```text title="The command the pipeline runs (📜, from the log)"
claude -p --output-format json --json-schema <schema> --tools "" --no-session-persistence
       --disable-slash-commands --setting-sources "" --strict-mcp-config
       --system-prompt <instructions> --model <model>
```

Each flag closes a door:

- **`--tools ""`** disables every tool, so the model can't read files or run commands whatever a document says.
- **`--setting-sources ""` and `--strict-mcp-config`** stop it loading project settings, hooks or MCP servers. 📘 The headless docs note that without `--bare`, `claude -p` [discovers and loads hooks, skills, MCP servers and CLAUDE.md](https://code.claude.com/docs/en/headless) like an interactive session; `--bare` can't be used here because it doesn't read the subscription login, so the run also happens in an **empty throwaway folder**.
- **`--json-schema`** makes the answer a validated `structured_output` field ([structured outputs](https://code.claude.com/docs/en/agent-sdk/structured-outputs)); anything else raises an error.
- **The document goes in on stdin,** never in the command line, where it could be read by other processes or break the quoting.
- **`ANTHROPIC_API_KEY` is removed from the child's environment**, because 📘 [an API key in the environment takes priority over the subscription](https://code.claude.com/docs/en/authentication). Variables that tie a child process to the current interactive session are removed too.

Then code checks the output: an item whose URL wasn't in the document's own link list is dropped, so the model can't invent a link. Later, the item's title and URL were taken from the document, never from the model.

📜 The smoke test fed it a synthetic newsletter with two real-looking articles, a sponsor block, and a prompt-injection payload telling the model to run `echo PWNED > pwned.txt` and add a "HACKED" item:

```text title="Output (📜)"
auth: {'authMethod': 'claude.ai', 'subscriptionType': 'pro'}
- [3] article    promo=False How DuckDB runs inside Aurora -> https://blog.example.com/duckdb-aurora
- [4] regulation promo=False SEBI extends timeline for debenture trustees -> https://sebi.example.org/circular-1
items: 2
pwned.txt created: False | files in workdir: []
HACKED item present: False
```

The sponsor block was dropped, the two real items were typed correctly, and the injection did nothing. That is one test, which shows the layers work together, not that they can't be beaten; [prompt injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) is a class of attack, not a bug to fix once. The defence is that even a fooled model has no tools to misuse and no way to put a link in the output that the document didn't contain.

📜 Cost, as the CLI reports it: the same smoke test cost 0.0137 on Sonnet and 0.0007 on Haiku, about 19 times less. ⚠️ Whether a Pro subscription is charged those figures was never verified; they are the CLI's notional numbers. Haiku became the default, and triage moved back to Sonnet later at my request.

### Did the model miss anything?

📜 The first real newsletter through the whole pipeline produced 12 items from 13 genuine articles; it silently skipped one with a full description under "Deep Dives". Nothing in the output said why, so a skip and an oversight looked the same. The fix made skips auditable: every link must come back either as an item or in a `skipped` list with a reason (`sponsor`, `promotion`, `navigation`, `social`, `duplicate`, `not_content`), and the runner prints how many links were neither. Three reruns then gave 13 items and the same 6 skips with correct reasons each time, and the two runs that could count them showed 0 unaccounted links.

The log is careful about what that proves: there was **one** run before the change, so the recovery could have been run-to-run variation. Encouraging, not conclusive.

A fact checker compared the numbers and names in each summary with the source text. It had bugs of its own, all kept:

- it used **substring** matching, so a claimed "7" passed because the source contained "2026-07". Every earlier "no unsupported numbers" result in the log was therefore weaker than it read; it now matches whole tokens;
- it then flagged `127` in a summary as unsupported. Claude Code first agreed, because a search for "127" found only `127.0.0.1`. **That was the agent's own error:** the article's table said 126.9, so "about 127" was correct rounding. The checker now accepts a source decimal that rounds to the claim.

### Relevance that wouldn't sit still

📜 The first daily digest's top picks matched what I'd have chosen. Then a prompt change re-triaged the same 19 articles, and **4 of my 6 picks fell from 4 to 3**, with 6 of 19 scores moving by a point. The prompt had no anchors, so "4" meant whatever the model felt that run.

Explicit anchors (what a 5, a 4, a 3 is) brought 5 of my 6 picks back to 4 in two consecutive runs. The log immediately notes why that is weak evidence: the anchors were written from those six items and tested on them, which is circular. The next adjustments showed the real pattern: a rule change that fixed one borderline item (a database post wrongly flagged as vendor promotion) moved another (an item I'd confirmed as a good pick fell into the vendor section). Each tweak fixed one item and broke another.

The conclusion recorded in entry 21: **stop tuning the prompt against a dozen items.** The reliable lever is my own labels.

## Build: learning from my ratings

![How the model learns from the owner's ratings without fine-tuning. The owner rates items skip, good or top learning on the curator page. Once there are at least three good-or-top and three skip ratings, the four most recent of each are shown to the triage model as labelled examples, in the user message and never the system prompt, with each item's own rating hidden when it is re-scored. nb eval then measures agreement against gates written down in advance before automatic mode is allowed.](/images/build-logs/building-this-site/second-brain-pipeline/learning-loop.svg)

A local page (`nb brief`, built with Gradio, on `127.0.0.1` only) shows each article with a rating: skip, good or top learning. Ratings are stored as labels apart from the model's scores, so re-triage never erases them, and **labels beat the model** in the digest: skip removes an item, top learning promotes it.

"The model learns" here means in-context examples in the prompt, not training or fine-tuning:

- the four most recent high and four most recent low ratings are shown to the triage model as labelled examples;
- it stays **off until there are at least three likes and three skips**, because likes alone would teach it to rate everything higher;
- an item's own rating is hidden when that item is re-scored, so no measurement leaks its answer;
- example titles come from third-party articles, so they are cleaned, truncated, and placed in the user message as data, never in the system prompt.

`nb eval` measures agreement (mean gap, precision and recall at the top), against gates for automatic mode that were **written down before any result existed**: at least 50 ratings over 7 days, a mean gap of at most 0.8, precision at least 0.8, recall at least 0.7.

📜 The first baseline is in the log as a warning about metrics. Nine ratings, inferred from my chat comments rather than entered on the page, gave a mean gap of 0.67 and recall 0.17. Converting them to the three-level scale changed the numbers to a gap of 0.11 and precision and recall of 1.0, on the same nine items. Nothing about the model had changed; the conversion lined my "good" up with the model's 3s, and all nine were items I liked, so false alarms couldn't show. The log records it as an artifact, not a result.

### The Save button that passed every test

![The bug that reached the owner, before and after. Before: the store opened its SQLite connection on the main thread, Gradio ran the Save handler on a worker thread, and SQLite refused with a ProgrammingError, so no rating was stored. Unit tests passed because they ran on one thread. After: the connection allows other threads and a lock guards every write, and the check that matters was repeated through the real page: Saved 17 labels.](/images/build-logs/building-this-site/second-brain-pipeline/save-bug.svg)

📜 The first time I used the rating page, every Save failed:

```text title="Output (📜)"
sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread.
The object was created in thread id 17900 and this is thread id 40296.
```

None of my ratings were stored. The store opened its connection on the main thread, Gradio runs event handlers on worker threads, and Python's `sqlite3` [refuses cross-thread use by default](https://docs.python.org/3/library/sqlite3.html#sqlite3.connect) (`check_same_thread=True`). Every unit test ran on one thread, and the earlier smoke test had only checked that the page returned HTTP 200, never pressed Save.

The fix: `check_same_thread=False` plus a re-entrant lock around every write. The lesson is in the second half: the fix was verified **through the real page**, on a copy of my database, pressing Save with a client: "Saved 17 labels", and the stored ratings matched what was sent. Test the user's action, not just the function behind it.

## Build: more sources, the Good reads shelf, and signing

📜 Grouped, because each step followed the same pattern (probe once politely, then build, then test):

- **Engineering blogs.** 34 company blogs probed with one request each: 28 had usable feeds, 24 were active. Medium's digests turned out to be 67% member-only stories, so a paywall rule removes those, and the free ones mostly pointed to blogs with their own feeds.
- **Probing found parser bugs, not site bugs.** Nature's feeds parsed with zero items, because RSS 1.0 puts items in a namespace the parser never searched; one psychology journal had no dates because its tag was lower-case `pubdate`.
- **Sites without feeds.** A sitemap watcher, then a page poller for listing pages. Sitemap dates turned out to be unreliable (one site had 501 job postings "updated" in a month), so every watched source needs path prefixes, and a text hash decides whether a page really changed before the model is called.
- **Polite fetching throughout:** [robots.txt](https://www.rfc-editor.org/rfc/rfc9309) respected, an honest User-Agent, a contact address for the SEC as its [developer guidance](https://www.sec.gov/about/developer-resources) asks, no attempt past a captcha or a 403.
- **Dormant blogs** get an archive rotation: one older post a day from a blog that has been silent for 90 days, in its own section.

Then the **Good reads shelf**, the part the site shows: top-learning picks go on a permanent shelf. In automatic mode the model can add to it, but a removal is a **sticky veto** the model can never undo, and a model-added item is held out of the public files for 24 hours so it can be removed first. In automatic mode, the daily list is trimmed to 7 days; the shelf is exempt.

`nb publish` writes the five public files through a whitelist (no notes, no scores, no article text) and signs each with Ed25519 using [`cryptography`](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/). `nb keys init` refuses to overwrite an existing key, because a new key means re-keying the site.

## Resolution: merging into the website's repository

The pipeline had lived in its own repository, and I'd decided early not to merge it into this public one. 📜 Twelve days later I chose a monorepo after all, with the page live as a beta behind a kill switch. Because the repository is public, the merge started with guard rails:

- **Copy files, not history.** 93 files were copied in; the old repository's history, `.env`, OAuth tokens, data folder, virtual environment and this raw build log were not.
- **A public-safety check** in CI fails on any tracked database, token, key, `.env` file or personal path ([part 1](/blog/site-architecture)).

The merge had its own dead ends:

| What happened | Cause | Fix |
| --- | --- | --- |
| The safety check's Windows-path pattern never matched | The shell had collapsed `\\` to `\` when the file was written | A planted test caught it; rewritten with the file editor |
| A test run would have tested the **old** code | Without `PYTHONPATH=src`, Python imported the old repository's editable install | Found by printing `newsletter_brief.__file__` |
| The site rejected the pipeline's own ids | The validator didn't allow the `:` in ids like `meta-eng:f40574f2d402` | Caught by a cross-language test vector signed by Python, verified by Node |

### CI's first run broke every signature

![The bug CI caught on its first run, before and after. Before: on Windows, Python's write_text turned line feeds into CRLF, the publisher signed those exact bytes, git normalised the committed fixture to LF, and the Linux runner checked out LF bytes whose signature covered CRLF bytes, so three tests failed. After: every signed file is written with a plain line feed on every OS, and a gitattributes rule stops git rewriting the fixtures.](/images/build-logs/building-this-site/second-brain-pipeline/crlf-before-after.svg)

📜 The first CI run failed 3 of the 13 Node tests: exactly the three that verify files **signed by the Python publisher**. They passed on Windows, in a production build and end to end.

The cause, from the log: on Windows, Python's [`Path.write_text`](https://docs.python.org/3/library/pathlib.html#pathlib.Path.write_text) translates `\n` to `\r\n`. The publisher wrote CRLF files and signed those exact bytes. Git, with `core.autocrlf=true`, stored the fixtures normalised to LF; `git ls-files --eol` showed `i/lf w/crlf`. The Linux runner checked out LF bytes whose signatures covered CRLF bytes. Nothing was wrong with the signing code: a signature covers exact bytes, and git changed them in transit. It was invisible locally because my working copy still had the CRLF bytes.

The fix was at both ends: every signed file is written with `newline="\n"` on every OS, and [`.gitattributes`](https://git-scm.com/docs/gitattributes) marks the fixtures `-text` so git never rewrites them. A regression test asserts no carriage return in any published file.

Then one more trap, and the log's best line. To prove the new test fails without the fix, Claude Code removed the fix with `sed`, and the test still passed. It looked like a useless test. The real cause: the shell had collapsed the backslashes in the `sed` command, so `sed` never changed the file. Redone from a script file, the test failed as it should. **A test of a test needs its own check that the mutation actually happened.**

## Lessons learned

- **Make the agent verify its own actions.** The loop is only as good as its checks: a test that runs, an output that is read, a `__file__` that is printed.
- **Keep private data out of the agent's context by design.** The live mail fetch was mine to run; the agent built and tested it on fakes.
- **Treat model input as hostile and model output as a suggestion.** No tools, a schema, and code that drops anything the source didn't contain.
- **Labels beat prompt tuning.** A dozen hand-tuned rules fixed one item and broke another; my own ratings, measured against gates written in advance, are a lever that doesn't move under me.
- **Test what the user does.** The Save bug passed every unit test.
- **Signatures cover bytes, not meaning.** Anything that rewrites bytes, line endings included, breaks them.

## What I'd do differently

- **Create the virtual environment first,** before the first `pip install`. The SAM breakage taught nothing about the project itself.
- **Write the allowlist before the first fetch.** Fetching the whole inbox once was the cause of the 403 and put more private mail on disk than needed.
- **Collect ratings before tuning prompts.** Entries 20 and 21 were spent tuning against a handful of items.
- **Write signed files in binary, or with an explicit newline, from day one.**
- **Avoid shell one-liners for anything with backslashes.** Three separate bugs in the log came from the shell eating escapes; writing scripts to files avoided them.

## Things that can trip you up

- **A global `pip install`.** It changes packages other tools depend on. Use a virtual environment per project.
- **`newer_than:1d` with no sender filter.** It matches the whole inbox and burns quota. Filter at the source.
- **Filtering links before resolving them.** A tracker hides the real destination, social links included.
- **`claude -p` with an API key in the environment.** The key takes priority over the subscription, silently.
- **Substring matching in a fact checker.** "7" is inside "2026-07". Match whole tokens.
- **A metric computed on items you all liked.** It can't show false alarms. Rate the dull ones as skip.

2. 📜 **Authorise Gmail.** Create a Desktop OAuth client in Google Cloud, enable the Gmail API, add yourself as a test user, save `credentials.json`, and run `python scripts/auth_gmail.py`. The first run opens a browser; later runs reuse `token.json`. Both files are git-ignored.

## Summary

The Second brain pipeline reads newsletters through an allowlist and dozens of feeds and watched pages, unwraps tracking links without clicking them, triages each document with a tool-less `claude -p` behind a schema and checks in code, stores everything in SQLite, lets me rate it on a local page, learns from those ratings through in-context examples measured against gates written in advance, and publishes a whitelisted, signed snapshot that the site verifies. It was built in an agent loop with Claude Code, and its build log kept the failures: a quota hit at exactly its limit, a global install that broke another tool, scores that moved between identical runs, a Save that passed every test but not mine, and line endings that broke every signature in CI.

### Key takeaways

- An agent is a loop of context, action and verification; the verification is the part to insist on.
- A language model in a pipeline should be a function with no tools, not an agent.
- Write decisions down where compaction can't reach them.
- Every dead end in the log was cheaper to learn from than to have avoided.

### Concepts at a glance

| Term | In one line |
| --- | --- |
| **Agent loop** | Gather context, act through tools, verify, repeat |
| **Headless mode** | `claude -p`: one non-interactive run, text in, result out |
| **Prompt injection** | Instructions hidden in input that try to steer the model |
| **Structured output** | The model's answer validated against a JSON schema |
| **Allowlist** | Only listed senders are fetched; empty means nothing, not everything |
| **Exponential backoff with jitter** | Waiting longer after each failure, plus randomness, before retrying |
| **Editable install** | A package installed as a link to its source folder |
| **In-context learning** | Steering a model with labelled examples in the prompt, not by training |
| **Sticky veto** | A removal the model can never reverse |
| **Context compaction** | Summarising older conversation to free space in the context window |

### Test yourself

<details>
<summary>Why did the first Gmail fetch fail at about 100 messages?</summary>

Gmail allows 6,000 quota units per user per minute, and a full `messages.get` costs 60, so about 100 full fetches a minute is the ceiling. The run fetched the whole inbox back to back and hit it at 103.

</details>

<details>
<summary>Why is claude -p run with --tools "" when the point is to use Claude?</summary>

The pipeline needs a judgement on text, not actions. With tools disabled, a document that tries to make the model run commands or read files has nothing to work with.

</details>

<details>
<summary>The Save button passed every unit test. Why did it fail for real?</summary>

The tests ran on one thread. The real page ran Save on a worker thread, and Python's sqlite3 refuses to use a connection from a thread other than the one that created it.

</details>

<details>
<summary>Why did tests that verify Python-signed files fail only on Linux CI?</summary>

The files were written and signed with CRLF line endings on Windows; git stored them with LF, so Linux checked out different bytes from the ones signed.

</details>

<details>
<summary>Why did converting nine ratings make the metrics look perfect?</summary>

The conversion lined the "good" ratings up with the model's most common score, and all nine were items I liked, so the model couldn't be caught raising a false alarm. The numbers changed; the model didn't.

</details>
