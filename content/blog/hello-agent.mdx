### What is an agent?
Speaking in terms of LLM world, the basic level interaction with an LLM happens through chat. User types in a prompt and LLM spits out an answer based on user's input or prompt.
Under the hood, the model predicts the response one token at a time, drawing on what it learned during training and on whatever context you put in the prompt. Depending on the 
model's size and compute power, this can significantly vary in terms of the quality of the output.

The limitation is that a chat is a single round trip: one prompt in, one answer out. The model can't go and check something, run code, look up fresh data or fix its own mistake. 
If the task needs five steps, I am the one doing the stitching, copying the output of step one into the prompt for step two, and so on.

An agent takes over that stitching. It automates repeated prompting with the LLM and runs multiple jobs behind the scenes to provide a holistic solution in place rather than just 
an answer which may not be the end solution to the user's request. In practice, it is a loop: the model decides what to do next, calls a tool (a search, a calculator, an API, a function 
I wrote), reads the result, and decides again, until it judges that the task is done. The LLM is the brain, the tools are the hands, and the loop is what ties them together.

This also explains why speed matters. One user request can turn into many model calls, so a slow model makes an agent painfully slow, and that is part of why I picked Groq for this build.

Agentic AI has been around for more than a couple of years and finally i wanted to give it a try in not just being a user of it but rather as a builder to understand a deeper technical 
perspective. Through pure coincidence, i came across Scaler's AI Bootcamp that has a guided plan to production of AI agents that should help me get my game into building Agentic AI 
workflows and i will be documenting my learnings.  

### What is the Strands Agents SDK?
Strands Agents is an open-source Python SDK for building AI agents. It was originally released by AWS. Its main idea is that you let the language model do the planning, instead of writing a rigid workflow yourself. You give the model a prompt and a set of tools. It decides which tool to call, reads the result, and keeps going until the task is done. This cycle is called the agent loop.

Why it suits a first agent:

- Small API. The core is one class, Agent. You can build a working agent in a handful of lines.
- Model-agnostic. Strands works with Amazon Bedrock, OpenAI, Anthropic, Ollama and others. Any OpenAI-compatible API also works. That includes Groq, which this post uses because it has a free tier.
- Tools are plain Python. Decorate a function with @tool and the agent can call it. Strands also ships a ready-made tools package (strands-agents-tools).
- Grows with you. The same SDK supports memory, multi-agent patterns, MCP and A2A, and deployment to AWS. You don't need to switch frameworks later.

The whole agent, in about 10 lines


```python
import os
from strands import Agent
from strands.models.openai import OpenAIModel

model = OpenAIModel(
    client_args={
        "api_key": os.environ["GROQ_API_KEY"],
        "base_url": "https://api.groq.com/openai/v1",
    },
    model_id="openai/gpt-oss-120b",
)

agent = Agent(model=model)
agent("Hello! Tell me a fun fact about AI agents.")
```

**What each part does**

- OpenAIModel tells Strands which model to talk to. Pointing base_url at Groq is the only change needed to swap providers.
- Agent(model=model) creates the agent and its loop. With no tools, it behaves like a chat model. Adding tools is what makes it act.
- Calling agent("...") sends your prompt through the loop and returns the response.

Takeaway: a first agent in Strands is a model plus an Agent wrapper. You add tools, memory and deployment on top of that as you need them.

### What is groq?
Groq is a company that runs open-source LLMs very fast. Groq doesn't train it's own frontier models. It hosts models like Open AI's gpt-oss, Llama and Qwen on custom chips and sells through an API called GroqCloud.

**Key Concepts:**
- LPU (Language Processing Unit): Groq's custom chip, built for inference, meaning running a trained model, not training one. It keeps model weights in on-chip memory, which is why responses come back so quickly. Speed is the selling point.
- GroqCloud: The hosted service. Call models over HTTP after creating an API key.
- OpenAI-compatible API: Groq's endpoint speaks the same protocol as OpenAI's. That's why the Strand's code only needs a different base_url and api_key. It's also why swapping providers later is easy.
- Free tier: no credit card is needed, and you are never charged on it. If you go over the limits, you get an HTTP 429 error. Limits apply per organization and per model.
    - Limits: sources disagree on the exact numbers. One recent page cites about 30 requests/min, 1,000 requests/day and 200,000 tokens/day for models like gpt-oss-120b. Check your own limits in the console before quoting figures in the post.
    - Developer tier: pay-as-you-go. It gives up to 10x higher limits and unlocks the Batch API.

**Why it fits a first agent**
- Agents call the model many times per task: plan, call a tool, read the result, repeat.
- Fast inference makes that loop feel responsive, and the free tier lets us experiement without spening money. The catch is the free tier limits.
- A looping agent can hit them quickly, so expect a 429 or two while we learn.

### Step 4: Give the agent a tool
**What a tool is**

- Is an odinary Python function that we hand to the agent. 
- Model can't run code itself and can only produce text. 
- When it wants to act, it asks for a tool call, code runs the function, and result goes back to the model as new context.
- Never sees the function body. Only sees description of the function.
- Function name: The tool's name. Pick a clear verb phrase like get_weather.
- Docstring: The tool's description. This is how the model decides when to use it.
- Type hints and Args: The input schema. They tell the model what arguments to pass and what types they are.

Using the follwoing example of fetching current time:

```python
@tool
def current_time(timezone: str = "Asia/Kolkata") -> str:
    """Get the current date and time in a given IANA timezone.

    Args:
        timezone: IANA timezone name, for example "Asia/Kolkata" or "America/New_York".
    """
    return datetime.now(ZoneInfo(timezone)).strftime("%A, %d %B %Y %I:%M %p %Z")


agent = Agent(model=model, tools=[current_time])
agent("What time is it right now in Bangalore and in New York?")
```
An LLM has no clock. It's knowledge is frozen at training time, so it can't answer the question by itself.

A tool fixes that which give model access to things it can't know or do on it's own.

**The function line by line:**
- `@tool`: registers the function with Strands and builds the description the model reads.
- `timezone: str = "Asia/Kolkata"` : the type hint tells the model to pass a string. The default makes the argument optional, so a call with no argument gives IST.
- Docstring: the summary line tells the model when to use the tool (it needs the current date or time). The `Args:` line tells it *what to pass*. The examples inside it matter most here. They show the model the exact format wanted, an IANA name like `America/New York` and not "NYC" or "EST".
- Body: `ZoneInfo(timezone)` loads the zone, `datetime.now(...)` gets hte current time in it, and `strftime` formats it such as text such as `Sunday, 25 October 2026 06:30 PM IST`. Returning a readable string means the model can quote it directly.

**What happens when you run the agent**

```python
agent = Agent(model=model, tools=[current_time])
agent("What time is it right now in Bangalore and in New york?")
```

Tool #1: current_time

Tool #2: current_time
- **Bangalore (India – Asia/Kolkata):** Sunday, 25 October 2026 09:16 PM IST  
- **New York (USA – America/New_York):** Sunday, 25 October 2026 11:46 AM EDT

- Prompt plus tool list go to the model. Sees the question and description of `current_time`.
- Model reasons about it. Decides it needs the clock nad that the question has two places, so it needs two lookups.
- The model translates place names. We mentioned "Bangalore" and "New York", but the tool wants IANA names. Model maps them itslef, which is why docstring examples matter:
    - `current_time(timezone="Asia/Kolkata")`
    - `current_time(timezone="America/New_York")`
- Strands runs Python. Each call executes the real function and returns a string like `Sunday, 25 October 2026 06:30 PM IST`.
- Results go back to the model. It now has both times and writes the final answer in plain english.

Steps 2 to 5 are the agent loop. May take two calls one after the other or together. Either way, we wrote none of the control flow. The model chose which tool to call, how many times, and with what arguments.

### From function to tool
An odinary Python function. Works when you call it, but an agent has no way to know it exists. 
```python
import requests


def check_server_status_plain(server_url):
    """Check if a server is responding."""
    try:
        response = requests.get(server_url, timeout=5)
        return f"Server is up. Status code: {response.status_code}"
    except requests.exceptions.RequestException:
        return "Server is down or unreachable"


print(check_server_status_plain("https://httpbin.org/get"))
```

This is a normal Python function that checks whether a website or server is reachable. The blog section calls it "plain" because it has no @tool decorator, no type hints and no Args: docstring. It works if you call it. An agent, though, only knows about functions you register as tools, so this one is invisible to it. The next step in your post would be adding @tool to turn it into a real tool.

Add three things and it becomes a tool the agent can discover and call: the tool decorator, type hints and a clear docstring (with an `Args:` section)
```python
from strands import Agent, tool


@tool  # Decorator
def check_server_status(server_url: str) -> str:  # Type hints
    """Check if a server is responding by making an HTTP request.

    Args:
        server_url: The URL of the server to check

    Returns:
        A message indicating whether the server is up or down
    """
    try:
        response = requests.get(server_url, timeout=5)
        return f"Server is up. Status code: {response.status_code}"
    except requests.exceptions.RequestException:
        return "Server is down or unreachable"
```

```python
agent = Agent(model=model, tools=[check_server_status])
response = agent("Is the staging server running? Check https://httpbin.org/get")
```


### First tool-enabled agent -- Tip Calculator 
```python
@tool
def calculate_tip(bill_amount: float, tip_percentage: float, num_people: int = 1) -> dict:
    """Calculate tip and split the bill among people.

    Args:
        bill_amount: Total bill amount in dollars
        tip_percentage: Tip percentage (e.g., 15, 18, 20)
        num_people: Number of people splitting the bill (default: 1)
    """
    tip = bill_amount * (tip_percentage / 100)
    total = bill_amount + tip
    per_person = total / num_people

    return {
        "bill": bill_amount,
        "tip": round(tip, 2),
        "total": round(total, 2),
        "per_person": round(per_person, 2),
    }


agent = Agent(model=model, tools=[calculate_tip])

response = agent(
    "The bill is $85. What's a 20% tip, and how much does each person pay if we're splitting it 4 ways?"
)
print("\n\nFinal answer:\n", response.message["content"][0]["text"])
```

Something that made me read further as to what's happening in the last three lines of the function

`agent = Agent(model=model, tools=[calculate_tip])`

- `model` is the Groq model object we setup earlier.
- `tools=[calculate tip] registers the function. Because of `@tool`, Strands has already built a description from the name, the docstring, and the type hints (`bill_amount: float`, `num_people: int = 1`). That description is ent to the model with every request.
- Nothing runs yet. This only builds the agent and it's loop.

`response = agent(
    "The bill is $85. What's a 20% tip, and how much does each person pay if we're splitting it 4 ways?"
)`

- Prompt and the tool description go to the model.
- Sees it needs a calculation. Pulls the values out of the sentence and requests a call: `calcualte_tip(bill_amount=85, tip_percentage=20, num_people=4`). This is why the docstring says "eg., 15, 18, 20". It tells the model to pass `20`, and not `0.2`.
- Strands run Python function and the returning dict goe sback to the model as a tool result. 

`print("\n\nFinal answer:\n", response.message["content"][0]["text"])`

Working from the inside out:

- `response.message` is the model's last message, as a dict shaped like `{"role": "assistant", "content": [ ... ]}`.
- `["content"]` is a list of content blocks. A message can hold several pieces, such as text, tool calls, or reasoning.
- `[0]` takes the first block.
- `["text"]` gets the string inside a text block.
- `"\n\nFinal answer:\n"` is only formatting: two blank lines, a label, and a newline. print puts a space between its two arguments.

So the line prints the model's closing sentence, after all the tool work is done.

### Multi-tool Sales Assistant 

Give the agent several small tools and it works out the order to call them in. One request -- "pull sales data and email a summary" -- becomes three tool calls.

```python
@tool
def get_sales_data(quarter: str) -> dict:
    """Retrieve sales data for a specific quarter."""
    return {"revenue": 1250000, "deals": 47, "quarter": quarter}


@tool
def analyze_sales(revenue: int, deals: int, quarter: str) -> str:
    """Calculate key metrics from sales data."""
    avg_deal = revenue / deals
    return f"{quarter}: ${revenue:,} revenue, {deals} deals, ${avg_deal:,.0f} avg deal size"


@tool
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email message."""
    print(f"\n[EMAIL] to={to} | subject={subject}\n{body}\n")
    return f"Email sent to {to}"


agent = Agent(model=model, tools=[get_sales_data, analyze_sales, send_email])
response = agent("Pull last quarter's sales data and email a summary to team@company.com")
```

You never wrote "first get data, then analyze it, then email." You gave the agent three tools and one sentence. The model worked out the order itself:
    - `get_sales_data(quarter="last quarter")` returns `{"revenue": 1250000, "deals": 47, ...}`
    - `analyze_sales(revenue=1250000, deals=47, quarter=...)` returns the summary string with the average deal size
    - `send_email(to="team@company.com", subject=..., body=...)` sends it
This is the shift from a chat to an agent. In a chat we'd be the glue between steps. Here the loop does it.

**Key Lessons**
- Chaining happens through results. The output of one tool becomes context for the next call. The model reads the dict from step 1 and copies those numbers into step 2's arguments.
- The model fills in arguments from our request. "Last quarter" became the quarter value, and team@company.com became to. The model also wrote the subject and body itself. Tool inputs come from the model's understanding of our sentence.
- Each tool does one small job. Fetching, analyzing and sending are separate functions. That makes them reusable and lets the model combine them in different ways for different requests.
- Docstrings and names are how the model chooses. "Retrieve sales data", "Calculate key metrics" and "Send an email message" are how it knows which tool fits each step. Clear names and descriptions matter more than clever code. The type hints (revenue: int, deals: int) also tell it what shape of data each tool expects.
- Tools are how the agent affects the world. get_sales_data reads, analyze_sales computes, and send_email has a side effect. Real actions are the part that makes agents powerful and also the part that needs care.

```python
@tool
def check_inventory(product_id: str) -> str:
    """Check if a product is in stock.

    Args:
        product_id: The product ID to check (e.g., "PROD-123")
    """
    inventory = {"PROD-123": 15, "PROD-456": 0, "PROD-789": 8}
    quantity = inventory.get(product_id, 0)

    if quantity > 0:
        return f"Product {product_id} is in stock. We have {quantity} units available."
    return f"Product {product_id} is currently out of stock."


agent = Agent(model=model, tools=[check_inventory])

# All of these work — the agent understands intent, not just keywords
agent("Is PROD-123 in stock?")
agent("Do we have PROD-456 available?")
agent("Check inventory for PROD-789")
agent("Can I order PROD-123 right now?")
```


One function. Four differently worded questions all end up calling it:

- "Is PROD-123 in stock?" -- check_inventory("PROD-123")
- "Do we have PROD-456 available?" -- check_inventory("PROD-456")
- "Check inventory for PROD-789" -- check_inventory("PROD-789")
- "Can I order PROD-123 right now?" -- check_inventory("PROD-123")
We never wrote code to match phrases like "in stock", "available" or "can I order". With traditional code we'd need keyword matching or a set of rules. Here the model reads the intent, decides the tool fits, and pulls out the product ID.


Key Lessons
- The model maps intent to the tool. "Can I order...?" doesn't mention inventory at all, yet the model realizes the answer depends on stock. That reasoning is the model's job. Your job is to give it a tool with a clear description.
- The docstring is the contract. "Check if a product is in stock" tells the model when to use the tool. The example (e.g., "PROD-123") tells it what format the argument takes, so it passes PROD-123 and not "product 123".
- Tools return facts, and the model turns them into replies. The function returns a plain sentence, and the model then phrases the final answer in its own words. You keep the logic (the lookup) in code and let the model handle the conversation.
- Handle the missing case in the tool. inventory.get(product_id, 0) means an unknown ID counts as out of stock instead of crashing. Notice what this costs you: a typo like PROD-12 says "out of stock", which is misleading. Returning "Product not found" would be more honest. This is a good beginner lesson, because the agent will repeat whatever your tool says, true or not.
- The agent is only as accurate as its tools. The model didn't know the stock level. The tool supplied it. That is the pattern: the model handles language, and tools supply real data.

[Agents that remember](https://scaler-content.github.io/Agents-that-remember/)

LLMs by default are stateless. That means if we opt out of a working session with a regular LLM chat conversation, it will not have any memory of that converstation as it's default behaviour.
Memory is how the agent gets that information back into the prompt. Without memory, every interaction feels transactional. With memory, agent can keep track of what we asked a while ago, keep important facts across sessions and adapt to our preferences and stay on track in long-running work.
