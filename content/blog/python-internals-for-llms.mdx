## What is Python? Why do inference frameworks choose it?

### How is a Python program executed?

#### How is the `python3` command found and executed?

- The OS searches for an executable file named `python3` along the directories in the `PATH` environment variable.
- After that, since Python is an interpreted language, the interpreter takes over. It reads the script, compiles it to bytecode and executes it, in a series of well-defined steps.

![The shell splits the PATH variable into folders and checks each in order for an executable named python3. The first match wins and the OS starts it as a new process](/images/ai-llms/llm-architectures/python-internals-for-llms/path-lookup.svg)

#### What does Python do when parsing app.py? What are the stages (compile, eval)?

There are four stages between your source file and a running program:

1. **Lexing.** The lexer (or scanner) reads the source code character by character and groups the characters into meaningful sequences called **tokens**. A token is a distinct unit such as a keyword, identifier, operator or literal.
    - This converts a raw string of characters into a structured sequence that the parser can process.
2. **Parsing.** The stream of tokens is checked against Python's grammar rules, to make sure the code is syntactically correct, and an **Abstract Syntax Tree (AST)** is built. The AST represents the hierarchical structure of the program and the relationships between its parts.
    - Each node in the tree is a construct in the source code, such as an expression, statement or declaration.
    - It is "abstract" because it leaves out concrete syntax such as parentheses and semicolons, and keeps only the structure that matters for interpretation.
    - It captures the relationships and dependencies between different parts of the code, which makes it a good intermediate representation for further processing.
3. **Compilation.** The AST is converted into **bytecode**, a sequence of instructions for the Python Virtual Machine (PVM). The bytecode is wrapped in **code objects**, which can be cached in `.pyc` files so later runs load faster.
    - Bytecode is a sequence of low-level, platform-independent instructions designed to be executed by the PVM.
    - It is an intermediate representation: more abstract than machine code, but more concrete than the source code or the AST.
    - It provides a layer of abstraction that makes Python's "write once, run anywhere" possible.
4. **Execution.** The PVM takes the bytecode instructions from the code objects and executes them.

![Source text goes through the lexer into tokens, the parser into an abstract syntax tree, the compiler into bytecode cached as .pyc, and the Python virtual machine executes it](/images/ai-llms/llm-architectures/python-internals-for-llms/python-execution.svg)

You can see the first three stages yourself. This sketch uses only the standard library:

```python
import ast
import dis
import io
import tokenize

source = "total = price * qty"

# Stage 1, lexing: the source text becomes a stream of tokens
for tok in tokenize.generate_tokens(io.StringIO(source).readline):
    print(tokenize.tok_name[tok.type], repr(tok.string))

# Stage 2, parsing: the tokens become an abstract syntax tree
tree = ast.parse(source)
print(ast.dump(tree, indent=2))  # indent=2 pretty-prints the tree

# Stage 3, compilation: the tree becomes a code object holding bytecode
code = compile(source, "app.py", "exec")  # "exec" means: compile a whole module
dis.dis(code)                              # disassemble: print the bytecode instructions
```

The built-in `eval()` function exposes the same pipeline at runtime. It takes a Python expression as a string, parses it, compiles it into a code object and has the PVM execute it:

```python
print(eval("2 + 3 * 4"))  # parsed, compiled and executed at runtime: prints 14
```

<Callout type="warn" title="eval() runs whatever it is given">

`eval()` is a powerful mechanism for dynamic code execution, which is exactly why it is dangerous. Never pass it text that came from outside your program.

</Callout>

#### What is Python bytecode? Is there an intermediate language?

- Bytecode is a low-level, platform-independent representation of Python source code. The interpreter first compiles the source into bytecode, which the PVM then executes.
- Bytecode is an intermediate language. It is the bridge between high-level Python source code and the machine-specific instructions that a CPU can execute.
- It is a crucial step for Python's portability: the same bytecode runs on different operating systems and architectures, as long as a compatible PVM is available.
- When the PVM "executes" bytecode, it doesn't typically translate each instruction into machine instructions on the fly (that would be just-in-time compilation). Instead, the PVM's pre-compiled native code performs the operation that each bytecode instruction describes.
- Since Python 3.11 the interpreter is also **specializing**. After an instruction has run a few times, it is swapped for a faster version for the types it actually sees: a `BINARY_OP` that keeps adding two integers becomes an integer-only add. `dis.dis(code, adaptive=True)` shows the specialized instructions. Python 3.13 added an experimental JIT compiler as well, off by default.

![For total = price * qty with price 12 and qty 5, two loads push 12 and 5 onto a value stack, a multiply replaces them with 60, and a store moves 60 into the name total](/images/ai-llms/llm-architectures/python-internals-for-llms/bytecode-stack.svg)

### What is Python's relationship with C?

#### What is CPython? Why is it written in C?

- **CPython** is the reference implementation of the Python language. When people say "Python", they typically mean CPython. It is written primarily in C and Python.
- The core interpreter, parser, bytecode interpreter and runtime system are implemented in C.
- The flow is CPython → bytecode → a C-implemented VM, which manages Python's objects, memory and calls to the OS.

| Reason | What C gives CPython |
| --- | --- |
| **Performance** | Execution speed, with low-level memory management and direct hardware access, and less abstraction overhead |
| **System integration and portability** | Direct use of the OS's APIs, which enables file I/O, networking and threading |
| **Extensibility and interoperability** | Wide access to different libraries |
| **Fine-grained control** | Control over memory allocation, deallocation and garbage collection, which helps prevent leaks and fragmentation |
| **Self-containment** | No dependence on another high-level language runtime |

Understanding CPython's C foundation also explains the **Global Interpreter Lock (GIL)**, which protects access to Python objects and stops multiple threads from executing bytecode at once.

#### When we use torch or numpy, who is actually running the code?

- Commands like `np.array(...)` or `torch.matmul(...)` are a high-level interface and orchestrator. They handle object creation, memory management (at the Python level) and the dispatching of calls to the routines that do the real computation.
- NumPy's backends link to **BLAS** (Basic Linear Algebra Subprograms) and **LAPACK** (Linear Algebra Package) implementations such as OpenBLAS, Intel MKL (Math Kernel Library) or ATLAS. These are highly optimised C, C++ and Fortran libraries that use instruction sets like AVX and AVX-512.
- PyTorch's CPU backend uses Intel MKL or OpenBLAS. On the GPU, NVIDIA's CUDA toolkit libraries such as cuBLAS and cuDNN come into the picture.
- CPython's ability to integrate with highly efficient C and C++ libraries is one of its most powerful advantages for high-performance computing.

![Your code calls the torch or numpy Python API, which dispatches into a C++ or C core, which calls BLAS libraries on the CPU or CUDA libraries on the GPU](/images/ai-llms/llm-architectures/python-internals-for-llms/who-runs-code.svg)

<Callout type="analogy" title="Python is the conductor, not the orchestra">

Python decides what to play and when. The compiled libraries underneath do the actual playing. That is why a heavy matrix multiplication written in Python is fast: almost none of its time is spent running Python.

</Callout>

#### How does Python call low-level C functions from high-level APIs?

- There are three main routes: the **C API**, the **`ctypes`** module, and specialised extension modules. The C API is the fundamental interface, interacting directly with Python objects and the interpreter.
- Python uses **reference counting** for automatic memory management. C extension code must manage reference counts carefully: increment (`Py_INCREF`) when it takes ownership, and decrement (`Py_DECREF`) when it gives ownership up. Getting this wrong causes memory leaks, dangling pointers or objects being freed too early.
- For CPU-intensive C extensions, the GIL can be released explicitly (`Py_BEGIN_ALLOW_THREADS`) during long-running C computations, and reacquired (`Py_END_ALLOW_THREADS`) before touching Python objects again. That allows real parallelism for C code that doesn't need the Python API, even inside a multi-threaded Python program.
- C functions designed for Python are compiled into `.so` (Linux, macOS) or `.pyd` (Windows) files. When you `import` the module, `PyInit_mymodule` is invoked, and it registers the C-implemented functions and data structures with the interpreter.

![Python code reaches C through an extension module using the C API, through ctypes loading a shared library at runtime, or through a binding generator such as Cython or pybind11](/images/ai-llms/llm-architectures/python-internals-for-llms/c-routes.svg)

Here is the simplest version of the idea, calling a C library function straight from Python with `ctypes`:

```python
import ctypes
import ctypes.util

# Load the C standard library (this sketch works on Linux and macOS)
libc = ctypes.CDLL(ctypes.util.find_library("c"))

print(libc.abs(-5))  # calls the C function abs() directly: prints 5
```

### Where does Python's "slowness" come from?

#### What is the GIL, and why does it limit multithreading?

- The GIL is a **mutex** that protects access to Python's objects, to keep CPython's internal memory management thread-safe. In effect, Python bytecode is executed one thread at a time.
    - It is a single, process-wide lock. Before any thread can execute Python bytecode, it must acquire the lock.
    - When a thread does I/O, or calls an external C library that explicitly releases the GIL, other threads can acquire it. Otherwise, threads yield the GIL periodically, based on a configurable instruction count or time slice.
- It simplifies the implementation of CPython by making object management thread-safe.
- It ensures that C extensions, which often manipulate Python objects directly, can't corrupt the interpreter's state.
- It **limits true parallelism for CPU-bound tasks.** Since only one thread can hold the GIL at any moment, only one thread can execute Python bytecode at any moment. Even with several CPU cores, a multi-threaded Python program doing CPU-heavy work effectively runs sequentially, with extra context-switching overhead on top. The system scheduler might place Python threads on different cores, but only one of them will be running Python code at a time.

<Callout type="info" title="The GIL is becoming optional">

Recent versions of Python include an optional "free-threaded" build, which runs without the GIL. It is still a separate build rather than the default, and this post describes the standard, GIL-based interpreter.

</Callout>

#### Why can't CPU-bound Python code scale up?

- Fundamentally, because of the Global Interpreter Lock. For CPU-bound tasks, the GIL means only one thread can hold the lock and execute bytecode at any instant.
    - The GIL's main purpose is to simplify CPython's memory management and keep its internal C data structures and C extension modules thread-safe. This design avoids the complex, fine-grained locking that would otherwise be needed for every Python object.
- In an I/O-bound operation, the Python thread can release the GIL while it waits for the I/O to finish. This makes multithreading effective for improving concurrency in I/O-bound scenarios.
- Strategies that get around the GIL's limits include **multiprocessing** (which uses multiple CPU cores in parallel), **C/C++ extensions**, and **asynchronous programming**.

![On the left, two threads take turns because they share one GIL. On the right, two processes each have their own GIL and run in parallel on separate cores](/images/ai-llms/llm-architectures/python-internals-for-llms/gil-threads-processes.svg)

#### Why is GPU code almost unaffected by the GIL?

- The computationally intensive parts are offloaded to external, low-level C and C++ libraries that explicitly release the GIL while they run.
- The GIL is bypassed in four steps:
    1. **Delegation to native code.** High-level Python code calls into its underlying C or C++ extension.
    2. **Explicit GIL release.** The extension dispatches the actual kernel to the GPU software, using CPython API functions to release the lock.
    3. **Asynchronous GPU execution.** The GIL stays free while the GPU computes.
    4. **GIL re-acquisition.** The extension takes the lock again, to keep access to Python objects and interpreter state thread-safe.
- The GIL mainly acts as a mutex for the interpreter's internal state and for Python bytecode execution. Almost all the work in GPU-accelerated computing is native code running on the GPU, outside the interpreter's control, so it doesn't contend for the GIL. The Python thread just starts the operation and then releases the lock, becoming a waiting observer instead of an active bytecode executor while the GPU works.

![A timeline of the Python thread, the GIL and the GPU: the extension releases the GIL when it launches a kernel, the GPU computes while other threads may run, and the GIL is re-acquired afterwards](/images/ai-llms/llm-architectures/python-internals-for-llms/gil-gpu.svg)

## Python and the OS: process, memory, syscalls

### What is a Python program inside the OS?

#### To the OS, is a Python program a process or a thread?

- Fundamentally, **a process.** The OS launches the CPython interpreter as a distinct process. That process loads the script, compiles it into bytecode and executes it.
- A Python program can itself manage multiple threads. What you mostly observe is a single process running the CPython interpreter, which may manage several OS threads internally, with the GIL limiting true parallel execution of Python bytecode.

#### Why does the OS need to assign it a PID, file descriptors, and a heap?

These are fundamental resources and identifiers that every OS process needs:

| Resource | What it is |
| --- | --- |
| **Process ID (PID)** | A unique numerical identifier that the kernel assigns to each running process |
| **File descriptors (FDs)** | Abstract, non-negative integer handles that the OS uses to represent open I/O resources |
| **Heap memory** | A segment of the process's virtual memory reserved for dynamic allocation, meaning memory requested explicitly at runtime |

The heap matters most for Python:

- It is crucial for data structures whose size isn't known at compile time, or whose lifetime must outlast a single function call.
- Nearly all Python objects (numbers, strings, lists, dictionaries, class instances, functions and modules) are allocated on the heap.
- The memory management system works mainly on this heap space, managing the lifecycle of those objects.

![A Python process has a PID, a virtual address space with code, libraries, a heap and a stack, and a file descriptor table, all kept by the kernel](/images/ai-llms/llm-architectures/python-internals-for-llms/process-anatomy.svg)

#### When does Python trigger a system call (syscall)?

- A syscall is the programmatic interface the OS kernel offers to applications, for accessing privileged resources that user-space programs can't touch directly.
- Python code doesn't invoke the kernel directly. Built-in functions such as `open()` or `socket.send()` go through the CPython interpreter, then the C standard library, and finally a `syscall`.
- Common scenarios are file I/O, network communication, process and thread management, memory allocation, system information and time.
- Syscalls are relatively expensive, because of the overhead of a **context switch** from user mode to kernel mode.

<Callout type="tip" title="Watch the syscalls yourself (Linux)">

On Linux, `strace` shows every syscall a program makes. Running `strace -f -e trace=openat python -c "open('x.txt')"` should show the `openat` call that sits underneath Python's `open()`.

</Callout>

### How does Python use memory and the file system?

#### When Python opens a file, how does it actually call open?

There are three layers between your code and the kernel:

- **High-level interface:** the built-in `open()` returns a file object, which hides the complexity of I/O.
- **Intermediate layer:** CPython's `io` module and its C functions.
- **Kernel gateway:** the fundamental mechanism through which user space requests a service from the OS kernel.

In order, for `file_obj = open('my_file.txt', 'w')`:

1. **Python's built-in `open()`** is called.
2. **CPython's C-level file I/O** takes over. Inside the C implementation, functions like `file_open_impl()` (from `Modules/_io/fileio.c` or similar) are invoked.
3. **The `libc` wrapper and the `syscall`.** The C standard library (`libc`, for example glibc on Linux) acts as a wrapper. Its `open()` function doesn't implement file opening itself. It prepares the arguments and executes the actual system call.

![A Python open call goes through CPython and libc, crosses into the kernel as a system call, and the kernel checks permissions and returns either a file descriptor or an error code that Python raises as PermissionError](/images/ai-llms/llm-architectures/python-internals-for-llms/syscall-path.svg)

#### If there's a file permission error, is it blocked by the OS or by Python?

- Fundamentally, **by the OS.** High-level file I/O operations are wrappers around system calls.
- The kernel does the access control checks, such as comparing the effective user ID (EUID) or group ID (EGID) against the file's ownership.
- If the required permissions aren't met, the request is denied at that core level. The OS kernel is the ultimate arbiter of resource access.

The flow of control, step by step:

1. **Python call.** Your code calls a file operation, such as `open()`.
2. **CPython wrapper.** The interpreter's C implementation translates this into a C function call.
3. **System call interface.** That C function makes the actual system call to the kernel.
4. **Kernel enforcement.** The kernel checks permissions. If they're denied, it returns an error code.
5. **Python exception.** The interpreter receives the error code and raises a `PermissionError`.

#### How do Python's memoryview and buffer map to physical memory?

1. **Object allocation.** A Python object (for example `bytearray(100)`) requests memory from the OS through C functions such as `malloc`. The OS allocates virtual memory pages to the process.
2. **Buffer protocol exposure.** The object implements the buffer protocol, which provides a `Py_buffer` structure containing the virtual address of its data.
3. **Memoryview creation.** A `memoryview` is created from the object and obtains the `Py_buffer` details, including that virtual address.
4. **Data access.** When the memoryview is used to read or write data (for example `mv[0]`), it computes a virtual address. The MMU (memory management unit) then translates that virtual address into a physical address on the fly, giving direct access to the data in physical RAM.

![A bytearray owns a block of memory, a memoryview points at the same block without copying, and the MMU translates virtual addresses to physical RAM](/images/ai-llms/llm-architectures/python-internals-for-llms/memoryview-buffer.svg)

```python
buf = bytearray(100)   # the object owns a block of memory
mv = memoryview(buf)   # a zero-copy view onto that same block (via the buffer protocol)
mv[0] = 255            # writes straight into buf's memory, with no copy
print(buf[0])          # prints 255
```

### Multiprocessing and threading: how does Python use multiple cores?

#### Why fork a new process instead of opening a thread?

- The reason comes straight from the GIL. Each new process has its own memory space and its own GIL.
- That lets Python bytecode run on a separate CPU core, achieving true parallelism. The `multiprocessing` module typically does this with the `fork()` system call.
- Threads are lighter and processes are heavier, but the choice is really dictated by the workload: **CPU-bound tasks benefit from multiprocessing**, while **I/O-bound tasks use threading effectively**, or can use `asyncio` for greater efficiency.

```python
from concurrent.futures import ProcessPoolExecutor


def burn(n: int) -> int:
    return sum(i * i for i in range(n))  # pure-Python, CPU-bound work


if __name__ == "__main__":  # required when processes are started with "spawn" (Windows, macOS)
    with ProcessPoolExecutor() as pool:  # each worker is a separate process with its own GIL
        # four jobs, which can run in parallel on separate cores
        print(list(pool.map(burn, [5_000_000] * 4)))
```

<Callout type="info" title="fork is not the only way to start a process">

`fork()` is the classic start method on Linux. Windows and macOS use `spawn` by default, which starts a fresh interpreter instead, and newer Python versions have moved the Linux default away from `fork` too. That is why the `if __name__ == "__main__":` guard above matters.

</Callout>

#### How does the OS allocate CPU to multiple Python processes?

- The OS allocates CPU to Python processes through its **kernel-level scheduler**.
- Each Python process is an independent execution unit, a distinct process from the OS's point of view. The scheduler handles all the processes competing for CPU time.
- Because the interpreter inside each process runs independently, the scheduler aims to maximise CPU utilisation and meet response-time requirements by sharing CPU time among the active processes.
- Scheduling uses **preemptive** algorithms together with **time slicing**, which gives each process a time slice (a quantum), and **context switching**, which saves the state of the running process and loads the state of the next one.
- For Python, multiprocessing is the standard way to use CPU cores while getting around the GIL. Multiple Python processes each have their own GIL and can run Python bytecode in parallel on different cores. They can be CPU-bound or I/O-bound: I/O-bound processes often yield the CPU, while CPU-bound processes use their full time slice.

![Two CPU cores run three Python processes, each getting a time slice before the scheduler switches to another](/images/ai-llms/llm-architectures/python-internals-for-llms/cpu-scheduler.svg)

#### Do Python subprocesses share GPUs?

- Yes, but how they share and interact is different from the CPU, and it needs careful thought about the GPU architecture and driver mechanisms involved.
- Subprocesses generally request and are given their own separate segments of VRAM.
- Python itself can't manage GPU hardware directly. It is an interface to low-level libraries, which make the actual API calls to the GPU driver to control the hardware.
- Advanced mechanisms such as explicit resource partitioning and inter-process GPU memory sharing also exist, for coordinated GPU usage.

![Several Python processes each have their own CUDA context and VRAM slice on one GPU, and the driver time-slices the streaming multiprocessors between them](/images/ai-llms/llm-architectures/python-internals-for-llms/gpu-sharing.svg)

## Python and the CPU: where does computation happen?

### How does the CPU handle Python's inference logic?

#### How does the CPU execute NumPy and PyTorch operations?

- Through the libraries from [who is actually running the code](#when-we-use-torch-or-numpy-who-is-actually-running-the-code): BLAS and LAPACK for NumPy, and MKL, OpenBLAS and oneDNN for PyTorch. On the CPU they add two levels of parallelism:
    - **Inside a core**, vector (SIMD) instructions process several numbers per instruction (next question).
    - **Across cores**, one large operation is split over several threads, which is called **intra-op parallelism** and usually runs on OpenMP. `torch.get_num_threads()` shows how many threads PyTorch uses, and `torch.set_num_threads(n)` changes it.
- Python makes one call per operation, so the interpreter's overhead stays out of the numerical loops.

#### Are these operations pure Python, or do they use SIMD / AVX instructions?

- The actual numerical computation in NumPy and PyTorch is offloaded to compiled, optimised routines that talk directly to the CPU's hardware features, including its SIMD and AVX instruction sets, for maximum performance.
- **SIMD** (Single Instruction, Multiple Data) is a class of instruction sets in which one CPU instruction performs the same operation on many data points at once.
    - This is fundamental for scientific computing and machine learning, where operations like vector additions, matrix multiplications and element-wise functions are applied to large arrays or tensors.
- **AVX** (Advanced Vector Extensions) is a set of SIMD instruction extensions developed by Intel (and supported by AMD). It widens the vector registers and adds new instructions for floating-point and integer operations.
    - These extensions are critical for performance in highly parallelisable workloads, which are everywhere in deep learning and high-performance computing.

![Scalar code needs 16 add instructions for 16 floats, while one AVX-512 instruction adds all 16 lanes at once](/images/ai-llms/llm-architectures/python-internals-for-llms/simd.svg)

#### How does PyTorch's CPU backend (MKL, OpenBLAS) get used by Python?

- Using MKL or OpenBLAS is a prime example of a **Foreign Function Interface**.
- PyTorch has a split architecture: a high-level Python API for users, and a low-level C++ core for computation. That core is called **ATen**.
    - ATen (A Tensor Library) is PyTorch's C++ tensor library. It provides the foundational data structures and operations, and acts as an abstraction layer for tensor manipulation that is independent of the hardware (CPU or GPU).
    - For CPU-bound operations, ATen doesn't re-implement optimised linear algebra from scratch. It links against highly tuned external libraries such as Intel MKL or OpenBLAS. These provide optimised BLAS and LAPACK functions, the building blocks for most deep learning operations (matrix multiplication, convolutions, reductions).

The path of a single call looks like this:

1. **Python API call**
2. **Data bridge** between the Python object and the C++ tensor
3. **Dispatch** to the ATen C++ kernel
4. **Backend function invocation** (MKL or OpenBLAS)
5. **Optimised CPU execution**
6. **Result packaging** back into a Python object

![One torch.matmul call passes through the Python API, a data bridge, the dispatcher, an ATen kernel, a backend library such as MKL or cuBLAS, and back into a Python tensor](/images/ai-llms/llm-architectures/python-internals-for-llms/dispatch-path.svg)

### Are Python threads truly parallel?

**Not for CPU-bound Python code**, because of the GIL. Threads give you *concurrency* (taking turns and overlapping waits), but not *parallelism* (running at the same instant). Which tool gives which:

| Tool | Runs Python bytecode in parallel? | Best for |
| --- | --- | --- |
| **Threads** | No: one thread holds the GIL at a time | I/O-bound work, and calls into C code that releases the GIL |
| **Processes** (`multiprocessing`) | Yes: each has its own interpreter and GIL | CPU-bound pure-Python work |
| **asyncio** | No: one thread, taking turns at each `await` | Many concurrent I/O waits, such as network requests |
| **C and C++ extensions** (NumPy, PyTorch) | Their native code can, with the GIL released | Heavy numerical work |

#### What operations does the GIL prevent from running in parallel?

- Operations that involve intensive computation purely within Python, without explicitly or implicitly releasing the GIL, are serialised.
- Examples are pure-Python arithmetic, manipulation of standard data structures, and user-defined functions that do heavy computation without delegating to external C libraries or doing I/O.
- Any operation on the Python object model that is guarded by the interpreter's internal locks.

#### Which built-in operations automatically release the GIL?

- **Blocking I/O.** Reading and writing files and sockets, `select`, `time.sleep()` and waiting on a subprocess all release the GIL while the thread waits for the operating system.
- **Some CPU-heavy built-ins.** `hashlib` releases it while hashing large buffers, and `zlib`, `bz2` and `lzma` while compressing.
- **Native libraries.** Most NumPy operations on large arrays, and most PyTorch operations, release it inside their compiled code.
- **Waiting on locks.** A blocked `threading.Lock.acquire()` or `queue.Queue.get()` releases it while it waits.
- **What never releases it:** pure-Python loops, arithmetic on Python objects, and work on lists and dictionaries.

#### Can multiprocessing bypass the GIL?

- **Yes.** Each process has its own interpreter, its own memory and its own GIL, so CPU-bound Python code runs in parallel on several cores.
- **The price.** Arguments and results are **pickled** and copied between processes, each process holds its own copy of the interpreter and of any data it loads, and starting a process takes much longer than starting a thread. For large arrays, `multiprocessing.shared_memory` avoids the copies.
- That is why data loaders use worker processes. PyTorch's `DataLoader(num_workers=4)` runs four processes that prepare batches in parallel while the main process feeds the GPU.

#### Where does asyncio fit in?

- **asyncio** gives concurrency on a single thread. Functions declared with `async def` are **coroutines**, and an **event loop** runs them one at a time. When a coroutine reaches an `await` on something that isn't ready yet (a network reply, a timer), it pauses, and the loop runs another one.
- Nothing runs in parallel, so the GIL never comes into play. The gain is that thousands of waits can overlap without thousands of threads.
- This is how LLM servers handle many users at once. vLLM's API server is an asyncio application (post 05), and the scheduler project in post 06 is built the same way.
- **The catch:** a coroutine that computes for a long time without awaiting blocks the whole loop. Blocking work belongs on a thread (`asyncio.to_thread`) or in another process.

![One thread runs an event loop that switches between three coroutines. Each coroutine runs for 8 milliseconds, awaits a network reply for about 90 milliseconds, then runs 8 more. While one waits, the loop runs another, so all three finish at 128 milliseconds instead of 324 if they ran one after another](/images/ai-llms/llm-architectures/python-internals-for-llms/asyncio-event-loop.svg)

```python
import asyncio


async def fetch(name: str, seconds: float) -> str:
    await asyncio.sleep(seconds)     # stands in for a network call: the loop runs others meanwhile
    return f"{name} done"


async def main():
    # three one-second waits overlap on one thread: about 1 second in total, not 3
    print(await asyncio.gather(fetch("A", 1), fetch("B", 1), fetch("C", 1)))


asyncio.run(main())
```

## How Python calls the GPU

### How does Python send data to the GPU?

#### What exactly does .to("cuda") do? How fast is it? Is it blocking?

- `.to("cuda")` is a method in deep learning frameworks like PyTorch. It transfers a tensor or model from the CPU's memory to the GPU's memory, so that NVIDIA's GPUs can apply their parallel processing power through CUDA.
- Its speed depends on the size of the data, the system bus bandwidth, the memory type and the CUDA environment setup.
- **By default the copy is blocking** from the CPU's point of view: the Python thread waits until the transfer has finished (`non_blocking=False`). Passing `non_blocking=True`, with the source in pinned memory, lets the copy overlap with other work.
- What *is* asynchronous by default is **launching GPU work**. A kernel launch is queued on the GPU and returns immediately, so the Python script carries on with the next lines of code on the CPU.
- Synchronization happens with `torch.cuda.synchronize()`, and whenever data is copied back from the GPU to the CPU.

![A tensor copied to the GPU goes from pageable host RAM through a pinned buffer and PCIe into HBM. A blocking copy stalls the Python thread, while a non-blocking copy overlaps with CPU work](/images/ai-llms/llm-architectures/python-internals-for-llms/h2d-copy.svg)

```python
import torch

x = torch.randn(1000, 1000)  # a tensor in CPU (host) memory
x_gpu = x.to("cuda")         # copy to GPU memory: blocks this Python thread by default
y = x_gpu @ x_gpu            # queues a kernel on the GPU and returns immediately
torch.cuda.synchronize()     # wait until the GPU has finished everything queued
```

#### Who decides which GPU to use? How are multiple GPUs managed?

GPU device selection follows a hierarchy of mechanisms, for both flexibility and control:

- **Default behaviour.** By default, frameworks such as PyTorch and TensorFlow target the first available GPU, usually identified as `cuda:0` (device 0).
- **Environment variables.** System-level variables influence GPU visibility and ordering without touching the code. The best-known is `CUDA_VISIBLE_DEVICES`. Setting `CUDA_VISIBLE_DEVICES="1,3"` makes only the GPUs with physical IDs 1 and 3 visible to the application, which then sees them as device 0 and device 1.
- **Explicit code.** Developers can assign tensors, models or operations to specific GPUs in code, with `.to("cuda:1")` or a `torch.device("cuda:2")` object.

```python
import os

os.environ["CUDA_VISIBLE_DEVICES"] = "1,3"  # must be set before CUDA is initialised

import torch

dev = torch.device("cuda:1")  # logical GPU 1, which is physical GPU 3 after the line above
```

Using several GPUs well is critical for scaling deep learning workloads, and there are several strategies:

| Strategy | What it does |
| --- | --- |
| **Data parallelism** | The most common way to raise training throughput: the model is replicated across GPUs, and each replica processes a different subset of the input data |
| **Model parallelism** | When a model is too large for one GPU's memory, its layers are split and spread across several GPUs |
| **Pipeline parallelism** | An evolution of model parallelism that reduces GPU idle time by pipelining micro-batches through the sequential model stages |
| **Sharding** (for example ZeRO, FSDP) | For extremely large models, even model parallelism may not be enough. Sharding spreads the model state (parameters, gradients, optimizer states) across GPUs to cut the memory footprint per device dramatically |

![Data parallelism replicates the model and averages gradients, tensor parallelism splits a layer's weights, pipeline parallelism streams micro-batches through layer groups, and sharding gives each GPU a slice of the training state](/images/ai-llms/llm-architectures/python-internals-for-llms/parallelism.svg)

#### Do you need to manually free CUDA memory? What does PyTorch handle for you?

- In PyTorch, you generally **don't** need to free CUDA memory manually. PyTorch has memory management that handles GPU allocation and deallocation for you.
- It uses a **caching allocator** for CUDA memory, a fundamental design choice that improves performance and simplifies memory management.
    - **How allocation works.** When you request memory (for example by creating a tensor on the GPU), the allocator first checks its cache for an already allocated but currently unused block that is big enough. If it finds one, it reuses it. If not, it asks the CUDA driver for a new block.
    - **How deallocation works.** When a tensor goes out of scope or is deleted, its GPU memory is *not* immediately returned to the CUDA driver. It is marked free and goes back to PyTorch's internal cache, ready for future allocations without the overhead of a CUDA driver call.

![A new tensor reuses a free cached block if one is big enough and otherwise calls cudaMalloc. A deleted tensor returns its block to the cache, and only empty_cache returns memory to the driver](/images/ai-llms/llm-architectures/python-internals-for-llms/caching-allocator.svg)

PyTorch handles several critical aspects of CUDA memory for you:

| What PyTorch handles | How |
| --- | --- |
| **Allocation and deallocation** | It manages the lifecycle of GPU memory. When a tensor is no longer referenced, its memory returns to PyTorch's cache |
| **Memory pooling** | The caching allocator keeps a pool of free blocks, which is what separates it from direct calls to `cudaMalloc` and `cudaFree` |
| **CUDA context management** | Memory is allocated within the active CUDA context, and operations happen in the correct device context |
| **Error handling** | Out-of-memory (OOM) situations get high-level error reports instead of cryptic driver errors |

Manual intervention is rarely needed, but there are a few cases where you interact with the cache:

```python
print(torch.cuda.memory_allocated())  # bytes currently used by live tensors
print(torch.cuda.memory_reserved())   # bytes PyTorch holds from the driver (includes free cached blocks)

torch.cuda.empty_cache()  # hand unused cached blocks back to the CUDA driver
```

- `torch.cuda.empty_cache()` clears PyTorch's internal cache and releases all unused cached memory to the CUDA driver. It's useful when you suspect fragmentation, after deleting large intermediate tensors, or to get an accurate reading of current GPU memory use. It does **not** free memory held by active tensors. It only empties the cache of blocks that were allocated but are no longer referenced.
- `torch.cuda.memory_allocated()` and `torch.cuda.memory_reserved()` show how much memory PyTorch is actively using and how much it has reserved from the CUDA driver, including cached free blocks.

At a low level, the caching allocator still talks to the CUDA Driver API:

- **Allocation:** `cudaMalloc(void** devPtr, size_t size)` allocates `size` bytes of linear memory on the device and returns a pointer in `devPtr`. PyTorch's allocator calls this when its cache is exhausted.
- **Deallocation:** `cudaFree(void* devPtr)` frees the memory that `devPtr` points to. PyTorch's allocator calls this when `empty_cache()` is invoked, or when PyTorch's overall memory request passes a threshold (less common in normal operation).

### How is computation on the GPU triggered?

#### Does calling model() execute on the GPU immediately, or is there lazy evaluation?

- A `model()` call on the GPU from Python is a nuanced blend of graph-based execution and optimised kernel launches, not a single atomic step.
- In an **immediate (eager) execution** model, each operation runs as soon as it is called, and the result is available straight away. This is more interactive and imperative.
- In **lazy evaluation**, operations define a computational graph without executing it right away, and the computation is deferred until something triggers it.
- By default, PyTorch runs in **eager mode**: the operations of the forward pass are performed one after another.
- TensorFlow 2.x also defaults to eager execution, but strongly encourages `tf.function`, which compiles Python code into a static TensorFlow graph. The graph is traced once, and later calls run the compiled graph directly on the GPU, which brings significant gains from global optimisations, memory pre-allocation and less Python overhead.

![In eager mode Python dispatches each operation and the GPU idles between small kernels. A compiled graph runs a few large fused kernels with one call](/images/ai-llms/llm-architectures/python-internals-for-llms/eager-vs-graph.svg)

#### How is a GPU kernel registered and launched?

1. **Definition.** Kernels are typically written in low-level, parallel-aware languages such as CUDA C/C++ for NVIDIA GPUs, or OpenCL C.
2. **Compilation.** The kernel source goes through a specialised compilation process that turns it into a device-specific binary format.
3. **Loading.** The GPU driver loads the compiled kernel library into GPU memory, which makes the kernel function accessible and ready for the device to run.
4. **Launch.** From the CPU (the host), a specific API call starts the kernel's execution on the GPU (the device).
5. **Arguments.** Pointers to data in device memory, and scalar parameters, are passed from the host to the kernel function running on the device.
6. **Queueing.** The runtime API call becomes commands that the GPU driver submits to the GPU's internal command queue, for asynchronous execution.

The queue is a **CUDA stream**. Work on one stream runs in order, while work on different streams can overlap, for example a copy on one stream while a kernel runs on another. PyTorch uses one default stream per device unless you create more.

![A kernel is written, compiled, loaded by the driver, launched with a grid and block configuration, queued in a stream, and run by thread blocks on the streaming multiprocessors](/images/ai-llms/llm-architectures/python-internals-for-llms/kernel-launch.svg)

#### How can you check which kernel an operation uses?

- This means looking into the runtime environment, using framework-specific introspection tools or low-level profilers.
- **PyTorch:** the most comprehensive tool is the **Torch Profiler**, which captures detailed execution traces with names and durations.
- **TensorFlow:** the TensorBoard profiler captures execution traces on both CPU and GPU, with visualisations of the operations, launches and usage.
- **Low-level NVIDIA profilers** (**Nsight Systems** and **Nsight Compute**) give a detailed timeline of CPU and GPU activity, including every CUDA kernel launch, API call, memory transfer and synchronization event, plus kernel-level analysis.

```python
from torch.profiler import profile, ProfilerActivity

# Record both CPU and CUDA activity while the model runs
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA]) as prof:
    model(x)

# A table of the operations and kernels that ran, with their timings
print(prof.key_averages().table(row_limit=10))
```

### How do the CPU and GPU synchronize?

#### Is .cuda() and .cpu() data transfer synchronous or asynchronous?

- **Synchronous by default**, like `.to("cuda")` above: the CPU thread waits until the copy has finished.
- `.cpu()` also has to wait for every kernel that produces the tensor, so it is a synchronization point as well as a copy.
- `.cuda(non_blocking=True)` and `.to(device, non_blocking=True)` make the copy asynchronous. From the host it overlaps with other work when the source is in pinned memory. Toward the host, the values aren't safe to read until the stream has been synchronized.

#### When does PyTorch force synchronization?

- Whenever the CPU needs the results of GPU computation, or when the order of operations across the host and device must be strictly enforced for correctness or resource management.
- **Implicit synchronization** happens through a barrier that blocks the CPU until the relevant GPU computation is done. Common triggers are copying a result back to the CPU (`.cpu()`), reading a single value with `.item()`, and printing a GPU tensor.
- **Explicit synchronization** is where developers insert synchronization points by hand, for fine-grained control, performance profiling or debugging.

#### What is torch.cuda.synchronize(), and when should you call it manually?

- It is a blocking call that makes sure all GPU operations on the current CUDA device, started by the host (CPU), have completed before the CPU moves on.
- Its fundamental purpose is to enforce synchronization between CPU and GPU. GPU operations are asynchronous: the CPU queues operations and carries on without waiting for the GPU to finish.
- Call it manually to **measure the execution time of GPU operations** accurately.
- Calling it can also **force an error to appear immediately** at the point of synchronization, which makes the origin of the problem easier to find.
- Call it to **access on the CPU data that was just modified on the GPU**: synchronizing guarantees that the GPU has finished writing the data to memory before the CPU tries to read it. This is especially true when using `.cpu()` on a tensor that has just been computed on the GPU.

![The CPU launches three kernels and carries on, then blocks at a synchronization point until the GPU has finished its queue and the result can be read](/images/ai-llms/llm-architectures/python-internals-for-llms/cpu-gpu-async.svg)

```python
import time

torch.cuda.synchronize()        # make sure earlier GPU work has finished
start = time.perf_counter()
y = model(x)                    # asynchronous: returns before the GPU is done
torch.cuda.synchronize()        # wait for the GPU, or we would only time the launch
print(time.perf_counter() - start)
```

## Summary

A Python program runs as source, tokens, an AST, bytecode and finally the PVM, all inside CPython, which is itself a C program. With `torch` and `numpy`, Python only orchestrates: the math runs in compiled C, C++, Fortran and CUDA libraries. That is also why the GIL, which lets one thread run bytecode at a time, slows down pure-Python threads but not GPU work. The operating system sees a process with a PID, a heap and file descriptors, and every file or network access is a syscall that the kernel checks. On the CPU, libraries use SIMD instructions and several threads per operation. On the GPU, copies block by default, kernel launches are asynchronous, PyTorch caches freed memory, and `torch.cuda.synchronize()` is how you wait for the results.

![A map of post 01 in four columns. What Python is: source compiled to bytecode, CPython written in C, torch and numpy calling C, and the GIL. The OS: a process with a PID and heap, syscalls through libc, permission checks in the kernel, and processes to get around the GIL. The CPU: BLAS and MKL, SIMD, threads inside an operation and the ATen dispatch path. The GPU: blocking copies, asynchronous kernels, the caching allocator and synchronization](/images/ai-llms/llm-architectures/python-internals-for-llms/summary-map.svg)

### Concepts at a glance

| Concept | In one line | Why it matters |
| --- | --- | --- |
| **Execution pipeline** | Source → tokens → AST → bytecode → PVM | What `python app.py` actually does |
| **Bytecode** | Platform-independent instructions for the PVM, specialized while the program runs | The interpreter's unit of work |
| **CPython** | The reference interpreter, written in C | Its C layer is how Python calls fast native code |
| **Python orchestrates** | `torch` and `numpy` dispatch to BLAS, MKL and cuBLAS | Heavy math barely touches the interpreter |
| **C API, ctypes and bindings** | Three routes from Python into C | How extension modules are built |
| **GIL** | One lock, so one thread runs bytecode at a time | Threads don't speed up CPU-bound Python |
| **Process** | A PID, virtual memory with a heap, file descriptors | What the OS sees when Python runs |
| **Syscall** | Python, then libc, then the kernel | The kernel, not Python, enforces permissions |
| **memoryview** | A zero-copy view of another object's buffer | Sharing memory without copying it |
| **Processes, threads, asyncio** | Parallel CPU work, overlapping I/O, one-thread concurrency | Picking the right tool for the workload |
| **SIMD and intra-op threads** | Many numbers per instruction, many cores per operation | Where CPU speed comes from |
| **ATen dispatch** | Python call → C++ kernel → MKL or cuBLAS | The path of one `torch` call |
| **Host-to-device copy** | `.to("cuda")`, blocking by default, faster from pinned memory | Data has to reach the GPU first |
| **Asynchronous kernels and streams** | Launches return at once and queue on a stream | Python runs ahead of the GPU |
| **Caching allocator** | Freed GPU memory goes back to PyTorch's cache | `memory_reserved` is not `memory_allocated` |
| **Synchronization** | `.item()`, `.cpu()` and `torch.cuda.synchronize()` wait for the GPU | Correct timings and correct reads |

### Test yourself

<details>
<summary>What are the four stages between app.py and a running program?</summary>

Lexing (source text into tokens), parsing (tokens into an abstract syntax tree), compiling (the tree into bytecode in code objects, cached as `.pyc`), and execution of that bytecode by the Python virtual machine.

</details>

<details>
<summary>Why can a CPU-bound Python program with two threads be no faster than with one?</summary>

The GIL lets only one thread execute bytecode at a time. The two threads take turns, and the switching adds overhead on top.

</details>

<details>
<summary>Why is GPU code almost unaffected by the GIL?</summary>

The extension releases the GIL while it launches work, and the computation runs on the GPU in native code, outside the interpreter. The Python thread only waits.

</details>

<details>
<summary>You open a file you have no permission to read. Who refuses?</summary>

The kernel. The `openat` syscall returns an error code, and CPython turns it into a `PermissionError`.

</details>

<details>
<summary>When should you use processes, threads or asyncio?</summary>

Processes for CPU-bound pure-Python work, threads for blocking I/O or C calls that release the GIL, and asyncio for many concurrent I/O waits on a single thread.

</details>

<details>
<summary>Is x.to("cuda") blocking? Is y = x @ x on the GPU blocking?</summary>

The copy blocks by default (unless `non_blocking=True` with pinned memory). The matrix multiplication only queues a kernel and returns at once, and the GPU runs it asynchronously.

</details>

<details>
<summary>Why does timing GPU code need torch.cuda.synchronize()?</summary>

Kernel launches return before the GPU has finished. Without synchronizing before and after, you only measure how long the launches took.

</details>

<details>
<summary>After del t, why doesn't nvidia-smi show the memory as free?</summary>

PyTorch's caching allocator keeps the block for reuse, so it still counts as reserved. `torch.cuda.empty_cache()` hands unused blocks back to the driver.

</details>
