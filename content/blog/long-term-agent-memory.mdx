## TL;DR

- **Three kinds of long-term memory:** semantic (what is true), episodic (what happened), procedural (how to act). Most agents need all three, kept per user.
- **Mem0** extracts facts from a conversation with a model, embeds them and keeps them per user; the agent searches them before answering. (Part 1, from October.)
- **Three memories, one answer:** a LangGraph pipeline adds keyword-matched facts, the customer's profile and an order lookup, then the model writes the reply. ✅ Asked whether an order could still be returned, Groq said "you're still within the window"; the data has no delivery date. Claude said it didn't have the date.
- **Memory that updates itself:** a model detects "keep it brief from now on", the preference changes in the same turn and is saved to disk. ✅ On Claude all three turns worked. On Groq the third turn crashed: the API itself rejected a JSON-mode reply as invalid, and the code only caught a parsing error.
- **The fixes in the course code are lessons too:** a default dictionary shared by every instance, and free-text JSON parsing that silently skipped updates. 📘

## Three kinds of long-term memory

| | Semantic | Episodic | Procedural |
| --- | --- | --- | --- |
| **Remembers** | Facts: what is true | Experiences: what happened | Skills: how to act |
| **Human example** | Delhi is India's capital | My last train to Pune was two hours late | How to ride a bicycle |
| **Agent example** | "Refunds within 30 days"; "this user is vegetarian" | "Last time, the shipping API rejected this order ID" | "To track an order: validate the ID, then query the order database" |
| **Typical store** | Key-value, SQL, knowledge graph, vector DB | Logs, an episodes table, vector DB | Prompts, JSON workflows, the agent's graph itself |

📘 From the lecture. Long-term memory lives across conversations, so it is keyed by the user: in LangGraph terms a **store** with a **namespace** such as `("u_42", "profile")`, where short-term memory is a checkpointer with a `thread_id`.

### Semantic memory: what is true

Facts not tied to a moment: business rules, product facts, and facts about a user. They can be **symbolic** (key-value pairs, SQL rows, a knowledge graph of triples such as *(Laptop, is_a, Electronics)*), **vector-based** (embedded statements, found by meaning) or **hybrid**. The lecture's knowledge-graph demo answers "what's a laptop's return window?" in two hops, Laptop → Electronics → 10 days, though no single fact says it. 📘

<Callout type="analogy" title="The company handbook">

Rules and facts on a new employee's desk, with no stories attached.

</Callout>

### Episodic memory: what happened

A diary of episodes: what was tried, when, and how it turned out. It lets an agent avoid repeating a failure and reuse what worked, the way a doctor thinks "this looks like the patient I saw last month".

![Episodic memory in use, from the lecture. A user asks 'Where is my order #78910?'. Episode 1, a failure: the agent asked for the order ID, then sent it straight to the shipping API, which answered 'Invalid ID format'. Episode 2, a success: the agent validated the ID first, turning it into ORD-78910, looked it up in the order database and confirmed the status. When a new request 'Where is my order #55321?' arrives, the agent retrieves both past episodes with the same goal, compares the outcomes, and follows the path that worked.](/images/ai-llms/agentic-ai/long-term-agent-memory/episode-paths.svg)

Episodes can be stored as logs, as rows (an `episodes` table and a `steps` table), as embeddings for "find similar past situations", or as a graph of events. 📘

### Procedural memory: how to act

Skills and workflows: the steps that work, stored as instructions in a prompt, as a JSON workflow in a database, or as the agent's graph itself. Where episodic memory says "this failed last time", procedural memory says "this is how we do it". 📘

## Part 1: Long-term memory with Mem0

In this exercise we build personal assistant agents that remember each user's preferences across conversations. Mem0 is the long-term memory, and a web search tool supplies fresh information.

### What is Mem0?

**Mem0** (pronounced "mem-zero") is an open-source memory layer. It gives an otherwise stateless model a persistent store of facts about a user, so the agent can recall them in later sessions.

It works in four moves:

1. **Add:** you pass in a conversation. Mem0 uses an LLM to extract the facts worth keeping, such as dietary preferences or working location, instead of storing the raw transcript.
2. **Store:** the facts go into a vector store, so they can be searched by meaning. Mem0 can optionally add a graph store to capture relationships between things.
3. **Update:** when a new fact contradicts an old one, Mem0 can update or delete the old memory instead of piling up duplicates.
4. **Search:** before each model call, search with the user's message, take the top few matching memories and put them in the prompt.

![Storing a memory: you say something, an LLM extracts facts, fastembed embeds them, FAISS stores them. Recalling: you ask, the model calls the memory tool, the query is embedded with the same model, FAISS returns the nearest facts](/images/ai-llms/agentic-ai/how-ai-agents-remember/mem0-pipeline.svg)

### Embeddings, FAISS and fastembed

The word "searched by meaning" hides three ideas that are worth understanding before the code.

**Embeddings.** An embedding is a list of numbers that captures the meaning of a piece of text. Texts with similar meaning get lists that are close together, and texts with different meaning end up far apart. This is how "Suggest a restaurant" can land near "I'm vegetarian", even though they share no words.

![A simplified two-dimensional map where food-related memories cluster together, the query Suggest a restaurant lands among them, and work-related text sits far away](/images/ai-llms/agentic-ai/how-ai-agents-remember/embeddings-map.svg)

**FAISS.** FAISS (Facebook AI Similarity Search) is an open-source library from Meta for fast similarity search over vectors. It is the "vector store" Mem0 uses here. A FAISS *index* is the data structure that holds all the vectors and answers the question "which stored vectors are nearest to this one?" quickly.

**fastembed.** Something has to turn text into those numbers. If you were on Amazon Bedrock, the course notebook would use Titan embeddings. Groq has no embeddings API, so here the embeddings run **on your own machine** with fastembed, a lightweight library from Qdrant. It runs small pretrained models through ONNX Runtime on the CPU, so it needs no GPU and no PyTorch.

Put together, when a user says "I'm vegetarian":

1. The Groq LLM extracts the fact.
2. fastembed converts that sentence into a vector with 1024 numbers.
3. The vector is stored in the FAISS index.
4. Later, a query like "Suggest a restaurant" is embedded by fastembed too, and FAISS finds the nearest stored vector.

<Callout type="tip" title="Store and search with the same model">

The same embedding model has to be used for storing and for searching. Vectors from different models aren't comparable. The vector size also has to match what the index expects. This notebook's memory tool expects **1024-dimensional** vectors (Titan's size), so we pick a 1024-dimension model.

</Callout>

```python
load_dotenv()  # reads GROQ_API_KEY from a .env file, if present

# Which Groq model to use. Falls back to gpt-oss-120b if GROQ_MODEL_ID isn't set.
MODEL_ID = os.getenv("GROQ_MODEL_ID", "openai/gpt-oss-120b")

# (on Groq), and an embedding model that indexes memories (local; see
# "A local embedder for Mem0" below).
os.environ.setdefault("MEM0_LLM_PROVIDER", "groq")
os.environ.setdefault("MEM0_LLM_MODEL", "openai/gpt-oss-20b")

# Skip the interactive "are you sure?" prompt when the agent stores memories
os.environ["BYPASS_TOOL_CONSENT"] = "true"

# Turn off Mem0's anonymous usage telemetry
os.environ["MEM0_TELEMETRY"] = "False"

# Keep Mem0's history database inside this course folder
os.environ["MEM0_DIR"] = os.path.abspath(".mem0_course")

# Start from a clean slate: the memory tool's local FAISS index and this course's Mem0 data
shutil.rmtree("/tmp/mem0_384_faiss", ignore_errors=True)
shutil.rmtree(os.environ["MEM0_DIR"], ignore_errors=True)
# Recreate the folder right away. Mem0 only creates it when it is first imported,
# so without this line, re-running this cell in the same kernel would leave Mem0
# with nowhere to put history.db ("unable to open database file").
os.makedirs(os.environ["MEM0_DIR"], exist_ok=True)

```

`load_dotenv()` is the key line for secrets. It reads the `.env` file and puts each line into `os.environ`, so `os.getenv("GROQ_API_KEY")` works as if you had set the variable in your shell. If there is no `.env` file, it quietly does nothing. Add `.env` to `.gitignore` so your key never reaches git.

Two kinds of assignment appear in this cell:

- `os.environ.setdefault(...)` sets a value only if it isn't already set, so you can override it from outside.
- `os.environ[...] = ...` always overwrites.

What the cleanup lines do:

- `/tmp/mem0_384_faiss` is where the Strands Mem0 tool keeps its FAISS index. Don't read the `384` in that folder name as the vector size: this notebook's embeddings have 1024 dimensions.
- Deleting it means the agent starts with no memories, so earlier runs can't leak into your demo.
- The next line deletes `MEM0_DIR`, which holds Mem0's own data, including its history database. Clearing both keeps the vectors and the history in sync, and clearing only one would leave memories without their history, or the reverse.

### A local embedder for Mem0

Mem0 accepts any LangChain `Embeddings` object, so a few lines wrap fastembed in that interface. We pick `mixedbread-ai/mxbai-embed-large-v1`, a larger and more accurate English embedding model with 1024 dimensions, to match what the memory tool's index expects. The resulting `MEM0_CONFIG` is passed to every Mem0 client in the notebook.

`langchain_core` is the small base package of LangChain. It supplies the `Embeddings` interface here, and [the previous post](/blog/how-ai-agents-remember#langchain-langgraph-and-state) explains the wider LangChain family.

```python
# TextEmbedding: FastEmbed's class that turns text into vectors. It runs the model
# locally on the CPU through ONNX Runtime, with no GPU or PyTorch needed.
from fastembed import TextEmbedding

# Embeddings: LangChain's abstract base class (the "interface") for any embedder.
# It only says "you must provide embed_documents and embed_query". Mem0 accepts
# embedders that follow this interface, so we make ours match it.
from langchain_core.embeddings import Embeddings

# A small adapter. FastEmbed does the real work, but Mem0 expects a LangChain-style
# object, so this class translates between the two.
class LocalEmbeddings(Embeddings):
    """fastembed (ONNX on the CPU) behind the LangChain Embeddings interface that Mem0 accepts."""

    def __init__(self, model_name: str):
        # Load the embedding model by name. The first run downloads the weights,
        # and later runs reuse the cached copy.
        self.model = TextEmbedding(model_name)

    # Used when storing: embed a batch of texts (the memories) at once.
    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        # model.embed() yields one NumPy array per text. LangChain expects plain
        # Python lists of floats, so .tolist() converts each array.
        return [vector.tolist() for vector in self.model.embed(texts)]

    # Used when searching: embed a single question or query.
    def embed_query(self, text: str) -> list[float]:
        # Reuse the batch method with a one-item list, then take the only result.
        # The same model for both methods keeps stored and searched vectors comparable.
        return self.embed_documents([text])[0]

# Create the embedder. That 1024-number size must match the dimension the FAISS
# index was created with, or searches will fail.
embedder = LocalEmbeddings("mixedbread-ai/mxbai-embed-large-v1")  # 1024 dims, matching the FAISS index

# Sanity check: embed one word and print the vector length. It should print 1024.
print("Embedding dimensions:", len(embedder.embed_query("hello")))

# Config dict handed to Mem0. "provider": "langchain" tells Mem0 to use an embedder
# object we built ourselves, instead of one of its built-in providers like OpenAI.
# "model": embedder is that object.
MEM0_CONFIG = {"embedder": {"provider": "langchain", "config": {"model": embedder}}}
```

LangChain splits embedding into `embed_documents` and `embed_query` because some models treat a query differently from a stored document, for example by adding a prefix. Here both do the same thing, which keeps the adapter simple.

### The system prompt

The system prompt sets the agent's role, its limits and how it should use memory. It is guidance only: the hard boundary between users is enforced by the tool binding in `create_agent` below, not by these words.

```python
SYSTEM_PROMPT = """You are a personal assistant for {user_name}.
You must not access or reveal any other person's information.
If you are asked a question about another person, politely refuse to answer.
Create helpful responses based on what you remember about {user_name}.
When {user_name} tells you about their preferences, store them in memory.
When {user_name} asks for something, first retrieve relevant memories, then use web search to find the most relevant answer."""
```

The `{user_name}` placeholders are filled in later with `.format(...)`, so one template serves every user.

### One agent per user

`Mem0MemoryTool(user_id=...)` binds the memory to one user. `PythonAgentTool` then wraps that bound function with Mem0's tool description, so the agent sees an ordinary `mem0_memory` tool, but it can only ever reach that one user's memories.

![Mona's agent holds a memory tool fixed to the user_id mona_mona, so it can read and write Mona's memories in the shared FAISS index but cannot reach another user's](/images/ai-llms/agentic-ai/how-ai-agents-remember/per-user-memory.svg)

`SequentialToolExecutor` makes the agent run tool calls one at a time. A model often saves several facts in one turn, and by default Strands runs those calls in parallel. Every call loads the same local FAISS file, adds a vector and writes the file back, so run in parallel they overwrite each other and memories are silently lost. Any tool that writes to a shared local file needs this.

```python
# @tool turns this function into a tool the agent can call. Strands builds the
# description the model sees from the function name, the type hints and the docstring.
@tool
def websearch(keywords: str, region: str = "in-en", max_results: int = 5) -> str:
    # The docstring is the model's only guide to this tool, so it states what the tool
    # does and what each argument means. The examples (in-en, us-en) show the format.
    """Search the web for up-to-date information.

    Args:
        keywords: The search query keywords.
        region: The search region, for example in-en, us-en, uk-en, wt-wt.
        max_results: The maximum number of results to return.
    """
    try:
        # Run a DuckDuckGo text search. It returns a list of dicts, each holding a
        # title, link and snippet. No API key is needed.
        results = DDGS().text(keywords, region=region, max_results=max_results)
        # Tools must return text for the model to read, so convert the list to a string.
        # An empty result gets a clear message instead of an empty string.
        return str(results) if results else "No results found."
    except Exception as e:
        # Return the error as text instead of raising. The agent sees what went wrong
        # (rate limit, network) and can retry or answer without search, not crash.
        return f"Exception: {e}"

# A plain helper, not a tool: the model never sees it. It turns a display name into an
# ID that Mem0 will accept.
def to_user_id(user_name: str) -> str:
    """Mem0 user IDs allow letters, digits, _ - . only."""
    # strip() removes surrounding spaces and lower() makes it lowercase, so "Mona " and
    # "mona" map to the same memory. re.sub then replaces every character outside
    # letters, digits, "_", "-" and "." with an underscore, e.g. "Bunny Kaushik" ->
    # "bunny_kaushik".
    return re.sub(r"[^A-Za-z0-9_\-.]", "_", user_name.strip().lower())

# Builds one agent per user, each with its own memory.
def create_agent(user_name: str) -> Agent:
    # The memory tool is bound to ONE user here, in code, not by the model.
    # Mem0MemoryTool is created with a fixed user_id plus our MEM0_CONFIG (the local
    # embedder). The model can't choose or change whose memories it reads, so one user
    # can't see another's.
    memory = Mem0MemoryTool(user_id=to_user_id(user_name), config=MEM0_CONFIG)
    # Wrap the memory function as a Strands tool: (tool name, MEM0_TOOL_SPEC with the
    # description and input schema the model sees, the function that runs when called).
    memory_tool = PythonAgentTool("mem0_memory", MEM0_TOOL_SPEC, memory.mem0_memory)
    return Agent(
        model=model,  # the Groq model object built earlier
        # SYSTEM_PROMPT is the template from the previous step; format() fills in the
        # user's name so the agent knows who it is talking to.
        system_prompt=SYSTEM_PROMPT.format(user_name=user_name),
        # The tools the agent can use: memory (hand-wrapped) and web search (via @tool).
        tools=[memory_tool, websearch],
        tool_executor=SequentialToolExecutor(),  # memory writes share one local file: one at a time
    )
```

![A sequence diagram: you send your preferences, the model calls the memory tool with a store action, the tool works for 6.4 seconds and returns, then the model writes its reply. Cycle 1 took 7.85 seconds and cycle 2 took 1.23 seconds](/images/ai-llms/agentic-ai/how-ai-agents-remember/agent-loop-store.svg)

- **Cycle 1** (566 tokens in, 120 out): the model read the message and decided to call `mem0_memory` with `action: store`. Then the tool ran.
- **Cycle 2** (881 in, 131 out): the tool result went back to the model, which wrote the friendly confirmation.

**Why cycle 1 took 7.85 s:** about 6.4 s of that was the tool. Storing a memory is expensive, because Mem0 calls the Groq LLM to extract facts, then embeds them with fastembed and writes to FAISS. Cycle 2 only had to write one reply, so it took 1.2 s. The output doesn't break the time down, so that split is inferred from the timings.

**Why input tokens went from 566 to 881:** cycle 2 resends the whole conversation plus the model's own tool call and the tool's result. That is why agents get more expensive as the loop goes on.

Other things worth noticing:

- **The model wrote the memory text, not the user.** The stored `content` is the model's paraphrase of the message ("User is a veggie lover…"). What gets remembered depends on how the model summarises.
- **The model only knows the store succeeded.** It said "I've noted that you…" but it can't see what was saved. Retrieval in a later session is what proves it worked.
- **`latencyMs: 0`** probably means this model adapter doesn't fill that field. The real timings are `timeToFirstByteMs` (1,056 ms here) and `cycle_durations`.
- **Empty fields:** `state={}`, `interrupts=None`, `structured_output=None` and `checkpoint=None` are features this run doesn't use.
- **`tracking_id` and `toolUseId`** are random IDs for tracing.

#### Why five searches?

Five separate web searches for one request is the agent loop at work. The log shows only the tool name, not the queries or the model's reasoning, so the explanation below is inference.

- **Where it fits:** `#2` was the memory lookup from before, and `#3` to `#7` come straight after it. So the agent read Mona's preferences first, then turned them into searches. "Restaurants in Bangalore" alone wouldn't satisfy "vegetarian, low-sodium, decaf, full-service".
- **You never asked for five.** The model chose that itself. Likely reasons, roughly in order of plausibility:
  1. **One search per constraint or angle,** such as vegetarian fine dining in Bangalore, then low-sodium options, then decaf availability.
  2. **One search per candidate.** After finding restaurant names, it looked up details for each one. The answer has four restaurants, which could fit this.
  3. **Retries after weak or failed results.** `websearch` catches errors and returns `"Exception: …"` as text, so the model can see a failure and try again. Free web search is often rate-limited, so some of the five may have been retries.
- **Why they appear one by one:** `SequentialToolExecutor()` runs tool calls one after another and never in parallel. The model may have requested them all at once or one per loop cycle, and the log doesn't distinguish those.
- **The cost:** each search result goes back into the model's context, so the final call carried a lot of input. That matters on Groq's free tier.

To find out exactly what happened, check the result object after the run:

```python
# response is whatever agent1(...) returned; assign it when you run the query
response = agent1("Find good restaurant options for me in Bangalore")

print("Loop cycles:", response.metrics.cycle_count)
m = response.metrics.tool_metrics["websearch"]
print("Calls:", m.call_count, "ok:", m.success_count, "errors:", m.error_count)
```

`call_count` should be 5, and `cycle_count` tells you whether the calls came in one batch or across several cycles. These are counts only. To see the query text itself you would need to print the tool inputs as they are made.

<Callout type="warn" title="An agent with search can still make things up">

Check the details in that answer before trusting any of it. The phone numbers look patterned (`+91 80 4155 2000`, `+91 80 4155 7777`), and claims like "they keep a decaf coffee bean stock" or "the menu shows low-sodium markers" aren't tied to a citation. Only two of the four restaurants have a source marker, and the `【1†source】` markers are leftover citation formatting from the model, not links. Models do invent plausible-looking contact details. Search gives the model fresh material, but it doesn't guarantee the final answer sticks to it.

</Callout>

## Part 2: three memories feeding one answer

Mem0 decides what to remember by itself. The course's `memory_demo_1.py` goes the other way: all three kinds of memory are plain Python dictionaries, so you can see exactly what reaches the model.

![memory_demo_1 as a LangGraph pipeline of four steps. A customer's question enters. Step 1, semantic memory, adds general facts that match keywords in the question, such as the 30-day return policy. Step 2 adds what is stored about this customer: name, preferences such as detail level, and recent interactions; the code calls this episodic memory. Step 3, procedural memory, follows fixed steps to look up the customer's orders. Step 4 sends all three to the model, which writes the reply. The memories are Python dictionaries, so the flow is easy to see.](/images/ai-llms/agentic-ai/long-term-agent-memory/three-memories.svg)

```python title="memory_demo_1.py (the three memory steps, shortened)"
def get_semantic_facts(self, state):              # 1. general facts, by keyword
    if "return" in state["user_query"].lower():
        relevant_facts["return_policy"] = self.semantic_memory["company_policies"]["return_period"]

def get_user_context(self, state):                # 2. what we know about this customer
    state["user_context"] = self.episodic_memory.get(state["user_id"], {})

def procedural_lookup(self, state):               # 3. a fixed procedure: this user's orders
    user_order_ids = self.user_orders.get(state["user_id"], [])
```

The fourth node puts all three into one prompt ("SEMANTIC KNOWLEDGE… EPISODIC MEMORY… PROCEDURAL RESULTS…") and asks the model for the reply, wired with `StateGraph` as a straight line of four nodes.

<Callout type="note" title="A naming mismatch worth noticing">

The code's "episodic memory" is mostly a **customer profile**: name, preferred contact, detail level, language, plus a few recent interactions. By the lecture's own definitions, the profile is semantic memory *about the user* ("this user is vegetarian"), and only the recent interactions are episodes. The demo works either way; the labels matter when you design real stores, because profiles and episodes are updated and searched differently.

</Callout>

Two test cases, on both providers:

| Question | Groq gpt-oss-120b | Claude Haiku 5.5 |
| --- | --- | --- |
| user_123 (Alice, "detailed"): "What's the status of my orders and what's your return policy?" | ✅ "Hello Alice", a table of ORD-001 (shipped) and ORD-002 (processing), the 30-day policy with conditions | ✅ The same two orders and the 30-day policy, without using her name |
| user_456 (Bob, "brief"): "Can you check the status of order ORD-003? I might need to return it." | ✅ Delivered, and **"you're still within the window"** | ✅ Delivered, $89.99; **"I don't have the delivery date, so please check… whether the window is still open"** |

✅ The second row is the lesson. The order store holds a status and a value, no delivery date. Groq told the customer the return window was still open, which nothing in its memory supports; Claude said what it didn't know. Memory makes an agent sound informed, and a model will fill the gaps between remembered facts unless the prompt tells it not to.

The explainer lists the rest of the demo's limits, and two are worth knowing before copying it: 📘

- **Keyword lookup misses synonyms.** "Can I get a refund?" contains no "return", so no policy is fetched. Real systems search facts by meaning ([the retrieval post](/blog/retrieval-for-agents)).
- **A missing order.** `user_789` owns `ORD-006`, which isn't in the order store, so the model is shown an empty `{}` for it.

## Part 3: memory that updates itself

`memory_demo_2.py` adds one node to the same pipeline: before answering, a model checks whether the user changed a preference, updates it at once (the **hot path** from [the previous post](/blog/how-ai-agents-remember#writing-memory-hot-path-or-in-the-background)), keeps an audit trail, and saves everything to `episodic_memory.json`.

```python title="memory_demo_2.py (the detector, shortened)"
json_llm = llm.bind(response_format={"type": "json_object"})     # JSON mode

result = json_llm.invoke(prompt)          # "...respond with ONLY a valid JSON object... or {}"
try:
    updates = json.loads(result.text)
except json.JSONDecodeError:
    updates = {}
if updates:
    self.episodic_memory[user_id]["preferences"].update(updates)
    json.dump(self.episodic_memory, f, indent=2)                    # saved to disk
```

![memory_demo_2 over three turns. Turn 1, 'What is the status of my orders and the return policy?': the detector finds no preference change, and the reply is detailed. Turn 2, 'Please keep your answers brief from now on': the detector returns detail_level brief, the preference is updated at once, saved to episodic_memory.json with an audit trail, and the same turn's reply is already brief. Turn 3, 'Can you give me an update on all my orders?': on Claude the detector found no change and the reply was a short list; on Groq gpt-oss-120b the JSON-mode call itself returned HTTP 400 'Failed to generate JSON', which the code did not catch, so the program stopped.](/images/ai-llms/agentic-ai/long-term-agent-memory/preference-update.svg)

```text output
TURN 2  — User requests preference change to 'brief'
🔄 Checking for PREFERENCE UPDATES...
   ✏️  Preference updated for user_123: {'detail_level': 'detailed'} → {'detail_level': 'brief'}
📝 RESPONSE:
Got it, I'll keep my answers brief.
Shipping takes **3-5 business days**.
```

✅ On Claude, all three turns worked: detailed, then brief in the same turn as the request, then a two-line list of orders. On Groq, turns 1 and 2 matched, and turn 3 ("Can you give me an update on all my orders?", which should give `{}`) stopped the program:

```text output
openai.BadRequestError: Error code: 400 - Failed to generate JSON. Please adjust your prompt. See 'failed_generation' for more details.
```

✅ With JSON mode on, Groq validates the model's output itself and returns an error instead of invalid JSON. That moves the failure from the `json.loads` line, which the code guards, to the model call, which it doesn't. Shivank switched the detector to JSON mode precisely because free-text parsing failed silently (📘 his list of changes: "models sometimes wrap JSON in fences… which made `json.loads` fail and silently skip the update"); on this provider the failure came back in a louder form. It is occasional, not systematic: ✅ repeating the same detector call five times for each of the two turn messages on the smaller `gpt-oss-20b` gave valid JSON 10 of 10 times. An occasional failure that kills the program is exactly the kind that needs catching. The fix is one more `except` around the call, treating any failure as "no change", which is what the original intended. I've kept the code as the course has it so the run stays honest; the failure is the point.

### Two fixes that are lessons in themselves

![Before and after for a bug Shivank fixed in memory_demo_2. Before: each MemoryDemo starts with self.episodic_memory = EPISODIC_MEMORY_DEFAULT, which is the same dictionary, not a copy. Updating a preference changes the default itself, so a second MemoryDemo in the same program starts with the changed values. After: copy.deepcopy(EPISODIC_MEMORY_DEFAULT) gives each instance its own copy, and the default stays as written.](/images/ai-llms/agentic-ai/long-term-agent-memory/shared-default.svg)

📘 From the explainer's list of changes to the original code:

- **A shared default.** `self.episodic_memory = EPISODIC_MEMORY_DEFAULT` gave every instance the *same* dictionary, so updating one user's preference also rewrote the default. `copy.deepcopy` gives each its own copy. In Python, assigning a dict never copies it.
- **Free-text JSON.** The detector parsed the model's text with `json.loads(result.content.strip())`; a reply wrapped in code fences made it fail and the update was silently skipped. JSON mode fixed that, with the caveat above.

And the limits that remain: 📘 the memory file is saved but never loaded, so every run starts from the defaults; the detector can invent keys (ask for "a formal tone" and `{"tone": "formal"}` becomes a new preference); and the contact method lives outside `preferences`, so "contact me by SMS" probably adds a new key instead of changing it.

## Part 4: short-term and long-term together

| | Short-term (previous post) | Long-term (this post) |
| --- | --- | --- |
| **What is stored** | Every message and tool result | Facts, episodes, procedures |
| **Scoped by** | `thread_id` | `user_id` (a namespace) |
| **Who decides what to save** | Automatic, every step | A model (Mem0, the detector) or your code |
| **Lifetime** | One conversation | Weeks, months |

The two aren't alternatives. A real assistant wants both: checkpoints so a conversation can continue, and long-term memory so it knows the user next week.

![Recent messages from the checkpointer and relevant facts from Mem0 both go into the prompt. After the model answers, the new state is saved to the checkpointer and any new facts are stored in Mem0](/images/ai-llms/agentic-ai/how-ai-agents-remember/memory-together.svg)

This diagram is the general pattern, not something either course notebook builds on its own; they use different frameworks, so combining them would take extra wiring.

## Things that can trip you up

- **Mismatched vector sizes.** The embedding model and the FAISS index must agree on the number of dimensions. In Part 1 that is 1024.
- **Different embedding models for storing and searching.** Vectors from different models aren't comparable.
- **Parallel writes to a local index.** Without `SequentialToolExecutor`, memories can be silently lost.
- **Unchecked search results.** An agent can sound confident about details the search never returned, or, as Groq did in Part 2, about details memory never held.
- **JSON mode is not a guarantee everywhere.** On Groq an invalid reply becomes an API error; catch it where you call the model.
- **Copying defaults by assignment.** Use `copy.deepcopy` for nested defaults.
- **Saving memory you never load.** Persistence needs both halves.
- **Profiles labelled as episodes.** Decide what each store holds before choosing how to search it.

## What I learned

Long-term memory is less about storage than about rules: what deserves to be remembered, under which key, and how it comes back. The two runs disagreed most where memory was silent. Memory gave both models facts, and one model filled the gap next to them with an invented one.

## What I'd do differently

Put "if a fact is not in the provided memory, say you don't know it" into the reply prompt of any memory-backed agent, and test it with a question whose answer is deliberately missing, like the return window here.

## Summary

Long-term memory keeps facts (semantic), experiences (episodic) and procedures (procedural) across conversations, keyed by user. Mem0 extracts and searches facts automatically; a hand-built pipeline makes every memory visible and shows how keyword lookup, a profile and a procedure feed one reply; a detector in the hot path lets memory update itself and persist. The runs added two warnings to the course's own: models fill gaps next to remembered facts, and JSON mode can fail as an API error on some providers.

### Concepts at a glance

| Term | In one line |
| --- | --- |
| **Semantic memory** | Facts: what is true, including facts about a user |
| **Episodic memory** | Experiences: what happened, and how it turned out |
| **Procedural memory** | Skills and workflows: how to do a task |
| **Namespace** | The key that keeps one user's long-term memory apart from another's |
| **Mem0** | A memory layer that extracts facts with a model and searches them by meaning |
| **FAISS** | A local library for searching vectors by similarity |
